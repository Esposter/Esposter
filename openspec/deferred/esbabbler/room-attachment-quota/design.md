# Room attachment quota

Message attachments are the upload path that matters for rooms with no **storage** bound. The interim bound is the [per-user storage quota](../../../specs/resource/storage-quotas/design.md), which leaves a room's total capped only by what its members upload between them; the room-scoped bound this page describes is still missing. Avatars, room images and game saves stay uncounted. What still applies per file is the room's `maxFileSizeBytes` check at presigned URL issuance — a declared-size gate, which an under-declaring client can exceed the same way it can anywhere else ([file uploads](../../../specs/architecture/file-uploads/design.md)).

**Why deferred.** Charging room attachments to the uploader's personal allowance is the wrong model: it makes one person's quota depend on how much they contribute to shared rooms, and it puts a number about chat in the resource explorer. The honest model is a **room-scoped** allowance — a room has a size, an owner sees it, and a room that fills up stops accepting attachments — but that needs an owner-facing surface (where the bar lives, who is warned, what happens at the limit) and a decision about who pays for a room nobody owns any more. None of that is worth building before rooms are large enough for the number to matter.

**What it would reuse.** Almost all of it: the ledger (`storageLedger` already keys on bucket and object key), the reserve at presigned URL issuance, and the object-create reconcile handler (`ReconcileStorageLedgerEntry`) — the event feed would take the message-assets bucket back, and the counter would move from the user row to the room row.

**Revisit when:** a single room's attachments pass a gigabyte, or the storage bill's message-assets share becomes visible next to resource assets — whichever comes first. The uploader-charged interim this trigger is measured against is set out in [storage quotas](../../../specs/resource/storage-quotas/design.md).

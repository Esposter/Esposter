# Session menu layer as a forwarding child

The world session's menu layer, one `MenuScreen` with a page body in each of its slots, would move out of the session root into a child component. The child would receive every value the pages read, report every action they take back to the handlers the root already binds, and mount the menu screen once. The root already mounts the HUD, the workshop, the screens, the statue and the challenge layers as children, and the menu layer is the one block of its template left inline.

**Why not:** the child forwards and decides nothing. The recorded build of it replaced a block of a couple of hundred template lines in the root with a mount of about a hundred lines and a child of more than five hundred, and the child declares again more than seventy props that each page already declares. It holds no state and no logic, so the package grows by more than the root sheds. [The design](./design.md) measures two cheaper shapes on the real file, one bundle of the props the pages share and pages that own their composables, and neither removes a meaningful share of the block either. The layer stays in the root, as the router table of an integration root.

The checker's defect has no part in this decision. The forwarding child failed the package typecheck because a component's event map loses its earliest events once the component declares more than sixteen, models included, without an error, and that is drafted as an upstream report in [the vize typecheck change](../../../changes/architecture-vize-vue-typecheck/reports/event-map-overload-cap.md). A cut that pays is by feature, with far fewer events than that limit, so the defect would not stop it. The code of the recorded build is kept in [the recorded build](./recorded-build.md).

**What would change this:** a measurement on the real file that shows a shape removing more lines from the root than it adds to the package, with the pages' fixtures and tests counted on the adding side.

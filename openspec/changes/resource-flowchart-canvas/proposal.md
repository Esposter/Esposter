# Flowchart Canvas

## Why

The Flowchart draws its diagram with Vue Flow (`@vue-flow/core`) and four of its plugin packages: the background, the controls, the minimap and the node resizer. Two things now make the choice of canvas worth taking rather than leaving to the deferred idea. First, [flowchart shapes](../resource-flowchart-shapes/design.md) extends the Vue Flow canvas and waits on this decision. Second, the [deferred flowchart's future](../../deferred/resource/flowchart-on-editor-core/design.md) names a revisit trigger, the headless editor core shipping with the page builder's webpage editor running on it. That trigger has fired: the webpage editor imports the core today (`apps/web/app/components/PageBuilder/Editor.vue`). The deferred page's three futures are still the open question, and this change decides between them with the costs measured against the repository's own admission standard.

The core has no graph or edge support yet (`packages/headless-block-editor/src` has no edge or graph type), so a headless graph model would be new work on top of a tree editor, not a reuse of one.

## What Changes

Recommended, and not yet built:

- Keep Vue Flow as the flowchart's canvas engine. The engine is a stop-list item in the [dependency admission](../../specs/architecture/dependency-admission/design.md) standard, and its pan, zoom, drag and connection behaviour is what the editor depends on today.
- Absorb the four plugin packages as the app's own components, each over the engine's public instance, as the admission standard's component-wrapper rule sets out. This releases the four `Keep — hold` rows in the dependency ledger, which exist only while this decision is open.
- Move the flowchart's shared models off the engine's runtime exports. Two enums the saved content stores (the path type and the arrowhead) become the models' own, with unchanged stored values, so no content migrates. The engine stays imported only by the canvas, its path functions and its components.

Not decided here, and listed as open choices below: a headless graph package, a second engine, and the timing of the [flowchart shapes](../resource-flowchart-shapes/design.md) change.

## Recommendation

**Option 1: keep Vue Flow as the engine, absorb its four plugin packages as the app's own components, and move the shared models off its runtime exports.**

The reasons, in the order the admission standard weighs them:

- The engine stays a stop-list item. A rewrite (option 2) would be a new engine the repository owns, which the standard treats as a standing cost, and its one reason to exist, a graph model shared with the page builder, does not hold until the core gains a graph shape. A rewrite is justified by measured bytes, imports and call sites, and the first task below produces those numbers before any engine decision is built on them.
- The four plugins are held only because this decision was open. Once it is taken they are small components over the engine's public API, which is the component-wrapper shape the standard already settles.
- The shared models importing the engine at runtime is the one real coupling problem. `GraphEdge` uses the engine's two enums as runtime values (`z.enum(ConnectionLineType)`), and the shared resource definition map reaches the server, so the server's schema depends on the engine's module. Owning those two enums removes the coupling without touching any stored value.
- It unblocks [flowchart shapes](../resource-flowchart-shapes/design.md) now, on the canvas it was designed for, rather than on a rebuild that could discard its work.
- Options 3, 4 and 5 each replace the engine with one whose licence, framework or ownership of the DOM is a larger cost than the one the flowchart carries today.

## Open choices for the owner

1. **Keep Vue Flow (recommended), or start a headless graph package.** Taking option 2 means first giving the headless editor core a graph shape, which is the question the deferred page names. If the owner wants it, that is a separate change, and this one's recommendation is the interim.
2. **Absorb the minimap and the node resizer too, or keep their two packages.** Both are pointer-driven. The resizer has no keyboard path today, and the admission standard's accessibility clause applies to any replacement of it. The bytes are not the reason either way.
3. **Whether [flowchart shapes](../resource-flowchart-shapes/design.md) proceeds on Vue Flow now.** Recommended: yes, once this change's decision is taken.
4. **Whether the deferred page is revived or stays deferred.** Its trigger has fired. Recommended: the decision is recorded in this change, and the deferred page stays until the owner chooses option 2, at which point it moves into `changes/` as the deferred page describes.
5. **Whether to evaluate one more engine before deciding.** Options 3 to 5 were compared on licence and fit from public listings, without a bundle measurement. If the owner wants a measured comparison with a non-Vue engine, the first task below is the measurement, and the next is a spike.

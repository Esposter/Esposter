- [ ] [Departure announcement order](../../specs/architecture/cloudflare-services/design.md) — every departure awaits the room object's `removeMember`, which drops the member from the room's online list and closes their sockets on that room, before the `leaveRoom` event goes out, so the other members' lists prune the leaver one Durable Object round-trip late. The await cannot fail the leave, since `announceRoomMemberDeparture` logs a rejected `removeMember` and goes on, so the only cost is that delay, and the order is what keeps the leaver out of the members the event reaches. Decide whether the removal-first order stays, with the added latency measured and written into the realtime design, or the announcement goes first and the removal follows. If the order flips, change `announceRoomMemberDeparture` and write the ordering into the realtime design in the same change
- [ ] [Client bundle weight](../../specs/architecture/dependency-admission/design.md) — the schema package builds one file per module, so an enum or a helper loads only its own module ([unbundled barrels](../archive/2026-11-08-architecture-unbundled-barrels/design.md)); what remains in the client's entry chunk is `drizzle-orm`'s schema core (tens of kilobytes gzipped) and every zod locale module (over a hundred), reached by the few dozen drizzle-bound names the client's input models import (the message entity constructors and the `select*Schema` derived from a table), since `drizzle-orm/zod` uses the zod namespace as a value. Weigh the second definition of each such entity the client needs, kept equal to its table by a test, which is a cost of its own, against what the entry chunk pays today. No client schema entry and no subpath for a helper is added: the build already lets a bundler drop what an import does not reach. The lazy `import()` of `re2js` and `emojilib`, so the startup plugin loads no `node-html-parser`, are cheaper and each is measured the same way before it stays
- [ ] [Per-task waiting](../../specs/architecture/fleet/design.md) — a task blocked on something outside its change carries a marker after its phase marker, as `- [ ] 1.5 [phase 0] [waits: genshin-assets-interface-art task 1.1] Export...`. `parseProposalTasks` reads the marker, and the entry's `waiting` and the change's pick phase consider only the open tasks that carry none, while `x-waiting` keeps only a blocker that holds the whole change. Today `x-waiting` is one change-level flag (`parseProposalMetadata.ts`, `readProposalEntries.ts`): `selectTakeableEntries.ts` hides a change with it set even when its tasks are free, and its prose repeats the tasks' blockers in many open changes. **Done when** the regex reads the marker into two model fields, tests cover the marked, unmarked and whole-change readings, the fleet spec has a scenario for it, the [change metadata](../../../.agents/skills/openspec/references/change-metadata.md) page and the [throughput fleet](../../../.agents/skills/throughput/references/fleet.md) page say the same, and each change's task-numbered blockers are moved into markers.
- [ ] [Shared topic namespace mock](../../specs/architecture/cloudflare-services/design.md) — `apps/web/server/services/realtime/publishTopics.test.ts` and `apps/jobs/src/services/realtime/publishTopics.test.ts` each hold the same `mockTopicNamespace` fake and `MockPublishedTopics` list, and both setup files repeat `Object.assign(env, { TOPIC: mockTopicNamespace })`, so twelve test files import it from one copy or the other. Moving it into `packages/db-mock` is blocked by a cycle the change must break first: `@esposter/db` devDepends on `@esposter/db-mock`, and the fake is typed by `TopicNamespace` from `@esposter/db`, so db-mock would import a type from a package that imports it. Decide the home of `TopicNamespace` (move the type into `@esposter/db-mock` or `@esposter/shared`, or type the fake structurally), whether db-mock declares the type dependency it then needs, and where the setup wiring lives. Then move the fake, repoint the importers and both setup files, and delete the two copies in the same change
- [ ] [Format pass pipeline shared by the check and the write](../../specs/architecture/monorepo-tooling/design.md) — `scripts/src/services/precheck/readUnformattedPaths.ts` and `scripts/src/services/format/formatFiles.ts` each run the same sequence: filter to the formattable paths, `chunkPaths`, `listDifferent` per chunk, and for a chunk it cannot finish, `readFormattedSource` and `checkIsRewritten` one file at a time. A shared helper cannot cover both without changing `formatFiles`' fallback, which writes each file as it goes, while the check only reads. Decide the failed-run contract first: keep the write-as-it-goes partial rewrite that `formatFiles.test.ts` pins, so the files before an unparsable one stay rewritten, or write nothing on a failed run, which the pre-commit hook would then need to match. Then write that contract into the monorepo-tooling design, extract the shared sequence as one helper both callers use, and let the fallback be a lazy walk of `{path, formatted}` so each caller keeps its own write. **Done when** a rule change to the fallback is made in one place, and `formatFiles.test.ts` and `readUnformattedPaths.test.ts` both pass against the one helper
- [ ] [Ancestor walk of the sorting rules](../../specs/architecture/lint-toolchain/design.md) — `checkIsNodeInsideDeferredFunction` (`scripts/src/services/oxlint/sorting/checkIsNodeInsideDeferredFunction.ts`) walks `node.parent` up to the given ancestor by identity and returns at the first deferred function, while `computeAncestors` (`computeModuleDependencies/computeAncestors.ts`) walks up to a statement by range and collects every ancestor that passes a guard, so the same loop shape is written twice with a different stop test and a different return. Folding the first into the second needs a decision: whether `computeAncestors` takes the stop test as a parameter and gets a short-circuit form for "any ancestor passes", since a collect-all walk would visit every ancestor a deferred-function check stops early on. Its stop must stay identity, because the range test skips a deferred arrow sharing its statement's range (commit `695bbcce97`). **Done when** the decision is written into the lint-toolchain design, the sorting rules' tests cover a deferred arrow sharing its statement's range, and the two walks are one function or the design says why they stay two
- [ ] [Build-folder headers from the module's resolved headers](../../specs/architecture/security-posture/design.md) — `apps/web/server/plugins/nuxtAssets.ts` restates the module's static resource headers (`Referrer-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`, `X-Permitted-Cross-Domain-Policies`) and the embedder policy as a second literal, so a change to a default in `packages/nuxt-security-module/src/services/getDefaultSecurityHeaders.ts` leaves the hook sending the old value on the responses the Worker writes under `/_nuxt/`. Its `X-Frame-Options` is `DENY`, which is the app's override in `apps/web/configuration/security.ts`, so the plugin is the resolved value and not the default. No test can pin it today: `apps/web` may not import the module's sources (its lint rule forbids a relative specifier into a package, and the module's `#src` alias resolves to the app's own `src`), and the module's `exports` declare no subpath for them. Decide the source: the module exports its resolved static headers as a subpath the app imports, or a generated virtual module carries them into the Nitro bundle the way the route rules template does. Then the hook reads that source, and a test in `apps/web` asserts the hook's headers equal the resolved static headers. **Done when** a change to one default fails that test, and the security-posture design names the source the hook reads
- [ ] [Checkout path in the unbundled-barrels test](../../specs/architecture/build-pipeline/design.md) — `scripts/src/workspace/packages/unbundledBarrels.test.ts` matches the checkout's own path only as neighbouring folder pairs (`CHECKOUT_FOLDER_PAIRS`). A checkout sitting directly under the common folder, such as `{home}/Esposter` with its pnpm store under `{home}/Library`, yields no pair that matches a `Esposter/packages/…` path, so a build that wrote `dist/Esposter/…` passes silently. The single-name match this replaced caught that folder, but the pair form was chosen so a checkout under a folder named like `vendor` or `pnpm` does not match. Decide the signal that flags the checkout's folder without flagging vendored paths, then write it into the build-pipeline design and the test in the same change. The test needs the infra package's build output, so it can run only after a full build. **Done when** a fixture checkout at `/Users/<name>/Esposter` fails the test, and CI's `/home/runner/work/Esposter/Esposter` layout still passes
- [ ] [Game data mirror key over every product's lock](../../specs/architecture/ci-caches/design.md) — the mirror's key, `.github/actions/game-data-mirror-key/action.yaml`, hashes the two lock paths it names, while `getHostedAssetProducts` declares every product and its lock. A third product's lock is missing from the key: its change leaves the key as it was, the restore exact-matches the old mirror, the fill step is skipped, and the new product's objects never reach the mirror the coverage shards read. The ci-caches design says the key covers every product's lock, so the claim and the workflow disagree. Decide how the key enumerates the locks: a glob (wider than the products, so it would also hash locks no product declares), a step that asks `pnpm hosted-assets` for the lock paths of `getHostedAssetProducts` and hashes them, or a list generated from the declarations. Weigh that the restore runs before the fill, on the built scripts, and that `build-packages` and the coverage job both read the key. Then the action derives the key from that source, and the ci-caches design names it. **Done when** a product added to `getHostedAssetProducts` changes the mirror key without any workflow edit, and a test fails when a declared product's lock is absent from the key
- [ ] [Template reaper against a concurrent read](../../specs/architecture/server-testing/design.md) — `packages/db-mock/src/services/removeAbandonedEntries.ts` stats a template, judges it unused, then `rmSync`s it, with no coordination against a run that renews the same template in between. A reader that picked the template before the removal can then fail: `utimes` in `getTemplateDirectory.ts` throws ENOENT if the removal lands between its `existsSync` and its renewal, and the `cp` in `createMigratedMockDatabase.ts` throws ENOENT if the removal lands after the renewal. The window is small and the threshold is thirty days, so it is rare, but no test pins either side. Decide the fix: a lock file the reaper and the readers take in turn, or the reader treating a vanished template as unbuilt and building it again, with the copy retried once. Then the server-testing design names the choice, and the reaper's judgement is checked again immediately before its removal. **Done when** a test forces the template to vanish between the read and the copy and the copy still returns a migrated database
- [ ] [Vue augmentation twin in the app's types](../../specs/architecture/monorepo-tooling/design.md) — `apps/web/app/types/vue.d.ts` and `packages/configuration/types/vue/dataAttributes.d.ts` each declare the same two `AllowedComponentProps` index signatures, the `data-*` and camelCase `data…` keys, so the set is written in two files. The monorepo-tooling design says the app restates the shared set on purpose, since Nuxt generates its own tsconfig and cannot extend the shared one, and the Vue tsconfig's include is the only place the shared file is read. Decide whether the app's tsconfig includes the shared augmentation file through Nuxt's `typescript.tsConfig` include, as `packages/genshin-world/tsconfig.json` includes it, which deletes the app's copy and changes the app's typecheck environment, or the twin stays and the design names both files as its two declarations. **Done when** the decision is written into the monorepo-tooling design, and either the app's copy is gone with `pnpm typecheck` in `apps/web` passing over the shared file, or the design says why both copies stay

# Roadmap

Open work, each item linking its proposal. Rationale lives in [serialization](../../specs/architecture/serialization/README.md).

## Next

- [ ] [Bench smoke switch on Windows](../../specs/architecture/benchmark-reporting/design.md#smoke-runs) — the root `bench:ci` script sets `BENCHMARK_SMOKE_RUN=true` with POSIX inline-env syntax, which pnpm's default Windows shell (cmd.exe) does not parse, so `pnpm bench:ci` fails there before Vitest starts with `'BENCHMARK_SMOKE_RUN' is not recognized`. Without the variable the run would fall back to the reporter path and rewrite the committed `*.bench.md` files. No other root script uses an inline env prefix, and no cross-env dependency is present. Decide the portable mechanism: a `cross-env` devDependency admitted through the dependency-admission page, a script-shell setting, or a Node runner that sets the variable and spawns Vitest. Then change the `bench:ci` script, the smoke-runs paragraph of the benchmark-reporting design and the bench skill's `running-benchmarks.md` in the same change
- [ ] [Duplicate-prose link targets](../../specs/architecture/monorepo-tooling/design.md) — the duplicate-prose check shingles every markdown link target's three-word windows as citations, so an ordinary trigram an anchor shares (`a kit is` from `#how-a-kit-is-read`) marks every occurrence of it in a shared run as a path word, and a fourteen-word run containing it falls to eleven prose words and is dropped unreported. Decide how a link target is matched: as its whole contiguous target in the run, not as trigram windows, which keeps a copied sentence that links an anchor reported. Then change `checkIsPathRun` and `readDuplicateProseFindings` to that rule in the same change, and let the `duplicateProse` workspace test go green on it
- [ ] [Vendored vuetify0 copy](../../specs/architecture/agent-configuration/design.md#vendored-skills) — `.agents/skills/vuetify0/SKILL.md` is hand-edited, with its generator markers and the marker lines of its counts, API and components sections removed, so it no longer matches the `computedHash` that `skills-lock.json` records for `skills/vuetify0/SKILL.md` from `vuetifyjs/0`, and the installer's update would re-copy the publisher's file and restore the markers. Decide where the correction lives: fix the publisher's file upstream and re-vendor, or record the local edit in the lock and the spec as ours. Then make the copy, the lock record and the spec agree in the same change
- [ ] [Batch agent ceiling](../../specs/architecture/agent-batches/design.md#why-it-runs-this-way) — the llm-delegation batch rule says a batch runs "at most 20 agents at once", a prose number no code, spec or constant publishes, so nothing fails when it drifts; the enforcement ladder keeps a rule with no mechanism at prose only, and the only `REVIEW_BATCH_*` caps in `scripts/src/services/review/constants.ts` govern review batches, not agent launches. Decide whether the ceiling becomes an enforced constant that a launch checks, or is dropped from the rule so the batch waves size themselves, then make the llm-delegation reference and this design agree in the same change
- [ ] [Departure announcement order](../../specs/architecture/cloudflare-services/design.md) — every departure awaits the room object's `removeMember`, which drops the member from the room's online list and closes their sockets on that room, before the `leaveRoom` event goes out, so the other members' lists prune the leaver one Durable Object round-trip late. The await cannot fail the leave, since `announceRoomMemberDeparture` logs a rejected `removeMember` and goes on, so the only cost is that delay, and the order is what keeps the leaver out of the members the event reaches. Decide whether the removal-first order stays, with the added latency measured and written into the realtime design, or the announcement goes first and the removal follows. If the order flips, change `announceRoomMemberDeparture` and write the ordering into the realtime design in the same change
- [ ] [Client bundle weight](../../specs/architecture/dependency-admission/design.md) — the schema package builds one file per module, so an enum or a helper loads only its own module ([unbundled barrels](../archive/2026-11-08-architecture-unbundled-barrels/design.md)); what remains in the client's entry chunk is `drizzle-orm`'s schema core (tens of kilobytes gzipped) and every zod locale module (over a hundred), reached by the few dozen drizzle-bound names the client's input models import (the message entity constructors and the `select*Schema` derived from a table), since `drizzle-orm/zod` uses the zod namespace as a value. Weigh the second definition of each such entity the client needs, kept equal to its table by a test, which is a cost of its own, against what the entry chunk pays today. No client schema entry and no subpath for a helper is added: the build already lets a bundler drop what an import does not reach. The lazy `import()` of `re2js` and `emojilib`, so the startup plugin loads no `node-html-parser`, are cheaper and each is measured the same way before it stays
- [ ] [Per-task waiting](../../specs/architecture/fleet/design.md) — a task blocked on something outside its change carries a marker after its phase marker, as `- [ ] 1.5 [phase 0] [waits: genshin-assets-interface-art task 1.1] Export...`. `parseProposalTasks` reads the marker, and the entry's `waiting` and the change's pick phase consider only the open tasks that carry none, while `x-waiting` keeps only a blocker that holds the whole change. Today `x-waiting` is one change-level flag (`parseProposalMetadata.ts`, `readProposalEntries.ts`): `selectTakeableEntries.ts` hides a change with it set even when its tasks are free, and its prose repeats the tasks' blockers in many open changes. **Done when** the regex reads the marker into two model fields, tests cover the marked, unmarked and whole-change readings, the fleet spec has a scenario for it, the [change metadata](../../../.agents/skills/openspec/references/change-metadata.md) page and the [throughput fleet](../../../.agents/skills/throughput/references/fleet.md) page say the same, and each change's task-numbered blockers are moved into markers.
- [ ] [Codemod pushes and the local check](../../specs/infra/review/design.md) — `running-checks` settles that typecheck and lint are CI's on every push, with a local run only to answer a red, yet the review-queue skill's codemod case has a session run the touched packages' typecheck and suites locally before a direct push to `main`, and the [architecture-package-imports](../archive/2026-11-16-architecture-package-imports/tasks.md) and [architecture-value-sets](../archive/2026-11-16-architecture-value-sets/tasks.md) tasks 2.1 require the same before their codemod pushes. Decide whether a codemod push is gated by a local typecheck (a carve-out the settled rule names) or by CI alone, with the review's own gate as the only other check. Then make `review-queue`, `running-checks` and both tasks agree in the same change
- [ ] [Reconcile re-reads](../../specs/architecture/client-data/design.md) — `reconcile` is documented as taking only a value the server issues (the [pinia mutation-actions](../../../.agents/skills/pinia/references/mutation-actions.md) page and the client-data spec's `reconcile` bullet), yet about twenty call sites use it to re-read a list or a count: the ScheduleDialog's job list, `scheduledMessageJob`'s count, `resource` and `post/comment` refreshes, `ResponseDeleteDialog`, and the rename of a name-sorted resource page (`useRenameResource`), whose re-read moves the row the spec says a write never moves. Decide whether `reconcile` may re-read server-ordered data, or whether such a re-read runs beside the write (and when, against a read the write may not have landed behind yet) and the rename's row move is written as its own rule. Then make the spec, the pinia page and every site agree in the same change
- [ ] [Created category position](../../specs/architecture/client-data/design.md) — the client-data spec says `reconcile` never moves a row, and its own `createRoomCategory` paragraph says `reconcile` takes the position the server appended the category at, which `roomCategory.ts` does by re-sorting the row. Decide which holds: the server's append position is taken by `reconcile` as the exception the spec names, with the no-move rule narrowed to say so, or the client keeps its appended position and a conflicting create is re-read beside the write. Then make the spec's two passages, `roomCategory.ts` and its test agree in the same change
- [ ] [Open-resource read owner](../../specs/architecture/resource/design.md#client) — `useResourceStore`'s `reloadResource` repeats the route-id guard (`getRouteParam`, `checkIsUuidV7`) and the after-await route check that `useReadOpenResource`'s `readResource` owns, so the same rule lives in `apps/web/app/store/resource/index.ts` and `apps/web/app/composables/resource/useReadOpenResource.ts`, and a change to one drifts from the other. The duplication is the design's split: the page's read is watched and ends with the page, while the store's reload is a raw read with no watch, so removing it means choosing whether the open-resource read belongs to the store, which `reloadResourceContent` needs, or to the composable. Decide that owner, then make the store, the composable and the resource design's paragraph on the open resource agree in the same change
- [ ] [Room topic watch without members or authors](../../specs/architecture/client-data/design.md#live-reads) — `useRoomUserSubscribables` takes the watch on the room's rows from its refresh read, but `useRefreshRoomUsers` returns before any read when a room has no member and no loaded author (`if (userIds.length === 0) return;`), so the executed query reads nothing and `watchTopics` sets no watch. A room opened empty, then filled with members, has no watch on its rows, so a later rename publishes unseen and the names on screen stay stale until the room is reopened. Decide whether `readUsersByIds` accepts an empty `userIds` (relaxing the `min(1)` input in `ReadUsersByIdsInput`, with the router and its tests), or the room's watch is anchored on another read the room always makes, such as its message list. Then make the refresh, the input contract and the subscribable agree in the same change
- [ ] [Shared topic namespace mock](../../specs/architecture/cloudflare-services/design.md) — `apps/web/server/services/realtime/publishTopics.test.ts` and `apps/jobs/src/services/realtime/publishTopics.test.ts` each hold the same `mockTopicNamespace` fake and `MockPublishedTopics` list, and both setup files repeat `Object.assign(env, { TOPIC: mockTopicNamespace })`, so twelve test files import it from one copy or the other. Moving it into `packages/db-mock` is blocked by a cycle the change must break first: `@esposter/db` devDepends on `@esposter/db-mock`, and the fake is typed by `TopicNamespace` from `@esposter/db`, so db-mock would import a type from a package that imports it. Decide the home of `TopicNamespace` (move the type into `@esposter/db-mock` or `@esposter/shared`, or type the fake structurally), whether db-mock declares the type dependency it then needs, and where the setup wiring lives. Then move the fake, repoint the importers and both setup files, and delete the two copies in the same change
- [ ] [Erase sweep retry past a failed room](../../specs/user/account-deletion/design.md) — the sweep's member-room step (`apps/jobs/src/services/account/removeAccountFromMemberRooms.ts`) tombstones each membership before its `removeMember` call, and `getMemberRoomIds` reads only live memberships, so a `removeMember` that throws leaves that room's online set, sockets and `leaveRoom` undelivered, and the queue's retry from the top skips the room. Unlike `announceRoomMemberDeparture`, which logs a rejected `removeMember` and goes on, the erase lets the failure end the run, so the handler's "a retry finishes what a failed run left" does not hold for this step. Decide between removal-first (the room call before the tombstone, which `RoomObject.removeMember`'s comment says every caller relies on not happening) and a retry-stable selection (the rooms named by a read taken before the tombstone, or a marker the room call clears). Then write the choice into the account-deletion design's sweep step 4 and make the sweep and its test agree in the same change
- [ ] [Owned-room removal notice](../../specs/user/account-deletion/design.md) — sweep step 1 says the room object's `deleteAll` sends the online members a `deleteRoom` event, but `RoomObject.deleteAll` sends none (17a892e1 removed the notice), and `deleteAccountOwnedRoom`'s comment says the members learn of the removal from the membership rows that go with the room. The hard delete of the room row cascades those rows silently (`usersToRoomsInMessage.roomId` is `onDelete: cascade`), so an online member and their user object keep listing the room until a reload, while the web `deleteRoom` path tombstones the memberships and calls `updateUserToRoom` on each user object. Decide whether an account's erase tombstones the memberships and tells the members the way the web delete does, or the removal stays silent and the design and the comment say so. Then change the sweep, the comment in `apps/jobs/src/services/account/deleteAccountOwnedRoom.ts` and step 1 of the account-deletion design in the same change

Then move the runner, repoint both suites and delete the copies in the same change
- [ ] [One wiki ceiling or two](../../specs/infra/claude-interface/per-character-voices/design.md) — `WIKI_FILE_MAX_BYTES` and `WIKI_API_MAX_BYTES` in `packages/genshin-persona/src/services/constants.ts` are both `32 * 1024 * 1024`, the second commented "the same ceiling for an API answer", and every API read (`readWikiFileUrls`, `readWikiPageText`, and the scripts' `readWikiApi` callers) names the second, so one value is written twice.

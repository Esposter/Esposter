# Roadmap

Open work, each item linking its proposal. Rationale lives in [serialization](../../specs/architecture/serialization/README.md).

## Next

- [ ] [Message kind registration](../../specs/architecture/serialization/azure-table-path/spec.md) — the table-read requirement says a new stored message kind is registered in the shared class registry as well as in `MessageTypeEntityMap`, while the [class registry's](../../specs/architecture/serialization/class-registry/spec.md) table-read scenario says the shared registry needs no entry for a new kind. The code registers per class: `JSONClassMap` is keyed by class name, so a kind that reuses a registered class needs only its `MessageTypeEntityMap` entry, and a new class needs an entry in both. Decide whether the registry entry is per kind or per class, then make the two specs say the same thing in the same change
- [ ] [Duplicate-prose link targets](../../specs/architecture/monorepo-tooling/design.md) — the duplicate-prose check shingles every markdown link target's three-word windows as citations, so an ordinary trigram an anchor shares (`a kit is` from `#how-a-kit-is-read`) marks every occurrence of it in a shared run as a path word, and a fourteen-word run containing it falls to eleven prose words and is dropped unreported. Decide how a link target is matched: as its whole contiguous target in the run, not as trigram windows, which keeps a copied sentence that links an anchor reported. Then change `checkIsPathRun` and `readDuplicateProseFindings` to that rule in the same change, and let the `duplicateProse` workspace test go green on it
- [ ] [Vendored vuetify0 copy](../../specs/architecture/agent-configuration/design.md#vendored-skills) — `.agents/skills/vuetify0/SKILL.md` is hand-edited, with its generator markers and the marker lines of its counts, API and components sections removed, so it no longer matches the `computedHash` that `skills-lock.json` records for `skills/vuetify0/SKILL.md` from `vuetifyjs/0`, and the installer's update would re-copy the publisher's file and restore the markers. Decide where the correction lives: fix the publisher's file upstream and re-vendor, or record the local edit in the lock and the spec as ours. Then make the copy, the lock record and the spec agree in the same change
- [ ] [Batch agent ceiling](../../specs/architecture/agent-batches/design.md#why-it-runs-this-way) — the llm-delegation batch rule says a batch runs "at most 20 agents at once", a prose number no code, spec or constant publishes, so nothing fails when it drifts; the enforcement ladder keeps a rule with no mechanism at prose only, and the only `REVIEW_BATCH_*` caps in `scripts/src/services/review/constants.ts` govern review batches, not agent launches. Decide whether the ceiling becomes an enforced constant that a launch checks, or is dropped from the rule so the batch waves size themselves, then make the llm-delegation reference and this design agree in the same change
- [ ] [Departure announcement order](../../specs/architecture/azure-services/design.md) — every departure awaits each device's removal from the room's Web PubSub group before the `leaveRoom` event goes out, so the other members' lists prune the leaver one hub round-trip late. The await cannot fail the leave, since `removeUserFromRoomGroup` never rejects, so the only cost is that delay, and the order is what keeps the leaver's connections out of the group once the event is announced. Decide whether the group-first order stays, with the added latency measured and written into the design, or the announcement goes first and the removal follows. If the order flips, change `announceRoomMemberDeparture` and the design's ordering sentence in the same change
- [ ] [Client bundle weight](../../specs/architecture/dependency-admission/design.md) — a client chunk shared by many routes holds `drizzle-orm`'s schema core and every zod locale module: the client imports the `@esposter/db-schema` barrel for its enums and form schemas, and `drizzle-orm/zod` uses the zod namespace as a value, so the locales cannot be dropped. Measure first with `pnpm ai:dependencies:score --sort bundle --analyze` whether that chunk sits on the first-load path of a route people open; only then weigh a client schema entry that imports no drizzle against the second definition of each entity it needs, kept equal to its table by a test, which is a cost of its own. The lazy `import()` of `re2js` and `emojilib` and a `jsonDateParse` subpath of `@esposter/shared`, so the startup plugin loads no `node-html-parser`, are cheaper and each is measured the same way before it stays
- [ ] [Vize server build cost](../../specs/architecture/vize-compiler/design.md#what-it-costs) — a clean production build of the app takes noticeably longer with the Vize module, all of it in the server bundle, where `vite-plugin-vize:sfc transform` is most of the profile while the client bundle takes as long as before; the cause is the per-file `compileSfc` call the server build makes, which has been slower since `@vizejs/native` 0.683.0 and is reported as [Vize issue 12044](https://github.com/ubugeeei-prod/vize/issues/12044); the item is done when a Vize release fixes it and a clean build is timed against the baseline, or when a measure here shows the fix is better made in the app.
- [ ] [Per-task waiting](../../specs/architecture/fleet/design.md) — a task blocked on something outside its change carries a marker after its phase marker, as `- [ ] 1.5 [phase 0] [waits: genshin-assets-interface-art task 1.1] Export...`. `parseProposalTasks` reads the marker, and the entry's `waiting` and the change's pick phase consider only the open tasks that carry none, while `x-waiting` keeps only a blocker that holds the whole change. Today `x-waiting` is one change-level flag (`parseProposalMetadata.ts`, `readProposalEntries.ts`): `selectTakeableEntries.ts` hides a change with it set even when its tasks are free, and its prose repeats the tasks' blockers in many open changes. **Done when** the regex reads the marker into two model fields, tests cover the marked, unmarked and whole-change readings, the fleet spec has a scenario for it, the [change metadata](../../../.agents/skills/openspec/references/change-metadata.md) page and the [throughput fleet](../../../.agents/skills/throughput/references/fleet.md) page say the same, and each change's task-numbered blockers are moved into markers.

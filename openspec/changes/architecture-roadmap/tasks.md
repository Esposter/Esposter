# Roadmap

Open work, each item linking its proposal. Rationale lives in [serialization](../../specs/architecture/serialization/README.md).

## Next

- [ ] [Message kind registration](../../specs/architecture/serialization/azure-table-path/spec.md) — the table-read requirement says a new stored message kind is registered in the shared class registry as well as in `MessageTypeEntityMap`, while the [class registry's](../../specs/architecture/serialization/class-registry/spec.md) table-read scenario says the shared registry needs no entry for a new kind. The code registers per class: `JSONClassMap` is keyed by class name, so a kind that reuses a registered class needs only its `MessageTypeEntityMap` entry, and a new class needs an entry in both. Decide whether the registry entry is per kind or per class, then make the two specs say the same thing in the same change
- [ ] [Duplicate-prose link targets](../../specs/architecture/monorepo-tooling/design.md) — the duplicate-prose check shingles every markdown link target's three-word windows as citations, so an ordinary trigram an anchor shares (`a kit is` from `#how-a-kit-is-read`) marks every occurrence of it in a shared run as a path word, and a fourteen-word run containing it falls to eleven prose words and is dropped unreported. Decide how a link target is matched: as its whole contiguous target in the run, not as trigram windows, which keeps a copied sentence that links an anchor reported. Then change `checkIsPathRun` and `readDuplicateProseFindings` to that rule in the same change, and let the `duplicateProse` workspace test go green on it
- [ ] [Vendored vuetify0 copy](../../specs/architecture/agent-configuration/design.md#vendored-skills) — `.agents/skills/vuetify0/SKILL.md` is hand-edited (commit `433613989b` removed its generator markers and the counts, API and components sections' marker lines), so it no longer matches the `computedHash` that `skills-lock.json` records for `skills/vuetify0/SKILL.md` from `vuetifyjs/0`, and the installer's update would re-copy the publisher's file and restore the markers. Decide where the correction lives: fix the publisher's file upstream and re-vendor, or record the local edit in the lock and the spec as ours. Then make the copy, the lock record and the spec agree in the same change
- [ ] [Batch agent ceiling](../../specs/architecture/agent-batches/design.md#why-it-runs-this-way) — the llm-delegation batch rule says a batch runs "at most 20 agents at once", a prose number no code, spec or constant publishes, so nothing fails when it drifts; the enforcement ladder keeps a rule with no mechanism at prose only, and the only `REVIEW_BATCH_*` caps in `scripts/src/services/review/constants.ts` govern review batches, not agent launches. Decide whether the ceiling becomes an enforced constant that a launch checks, or is dropped from the rule so the batch waves size themselves, then make the llm-delegation reference and this design agree in the same change

# Package

The store is a workspace package, `packages/keyframe-store`, published like the repo's other generic libraries ([monorepo tooling](/docs/architecture/monorepo-tooling)).

## Why its own package

Three properties decide it, and each would be lost by putting the code anywhere else.

**It has more than one consumer.** The app server writes versions and reconstructs them; the Functions host collects objects when a resource is purged. That clears the bar a shared home requires, so the code cannot stay beside a single caller in `packages/app`.

**It must not know about Azure.** The store's only contact with storage is an injected interface of four methods. That is what makes it testable and benchmarkable against an in-memory map, with no emulator, no container client and no mock package — and a benchmark that measures the codec instead of the network is the only kind whose numbers mean anything. Putting it in `@esposter/db` would put it behind a package whose whole purpose is Azure and Drizzle clients, and the dependency would flow the wrong way.

**It is a general library, not an Esposter concept.** Nothing in it mentions a resource, a revision or a quota. `@esposter/shared` is the client-safe universal package and this is node-only, reaching for `node:zlib` and `node:crypto`; `@esposter/shared-node` is the benchmark reporting tooling. Neither is a home for a storage codec, and a package that is genuinely reusable is one the repo publishes rather than hides.

The name states the mechanism rather than the application, so it reads correctly from outside the repo.

## Shape

A node-only published package built with the node tsdown factory, extending `tsconfig.node.json`, re-exporting the shared TypeScript ESLint config, with its barrel generated by ctix and never hand-written. Its runtime dependency is `@esposter/shared` alone, for the neverthrow helpers every fallible path returns through; the codec and the hash come from node itself, so the package adds nothing to the dependency catalog.

```text
packages/keyframe-store/
  src/
    constants.ts                  the compression level, window bounds and promotion ratio
    createKeyframeStore.ts        the factory — the only entry point a consumer calls
    models/
      KeyframeStore.ts            the returned interface
      KeyframeStoreOptions.ts     the tunables, each defaulted from constants
      ObjectStore.ts              the injected backend
      WrittenVersion.ts           what a write reports back
    services/
      decodeObject.ts             header parse plus decompression
      encodeObject.ts             header build plus compression
      getContentAddress.ts        the plaintext hash
      getWindowLog.ts             the window derived from dictionary and input size
```

Every file holds one export, and the object header's layout lives with the two functions that read and write it rather than in a schema of its own — a format nothing else parses does not need a parser exported for it.

## API

```ts
export interface ObjectStore {
  checkIsStored: (key: string) => Promise<boolean>;
  delete: (keys: string[]) => Promise<void>;
  // A byte count reads only the object header, which is what makes a deduplicated write cheap. Azure serves
  // It as a ranged download; an in-memory backend slices
  read: (key: string, byteCount?: number) => Promise<Uint8Array | undefined>;
  write: (key: string, bytes: Uint8Array) => Promise<void>;
}

export interface WrittenVersion {
  // The keyframe this version decodes against, empty when the version is itself a keyframe — which is also
  // How a caller knows the lineage anchor moved
  baseHash: string;
  hash: string;
  isDeduplicated: boolean;
  plaintextBytes: number;
  // What the owner is charged, and zero for a version whose content the store already held
  storedBytes: number;
}

export interface KeyframeStore {
  // Takes the hashes an eviction released and the hashes still named by surviving rows, and returns the
  // Objects it deleted, so the caller can credit their bytes back
  collect: (releasedHashes: string[], retainedHashes: string[]) => ResultAsync<string[], Error>;
  read: (hash: string) => ResultAsync<Uint8Array, Error>;
  // The anchor is the caller's state, empty for a lineage that has none yet
  write: (plaintext: Uint8Array, anchorHash: string) => ResultAsync<WrittenVersion, Error>;
}

export const createKeyframeStore: (objectStore: ObjectStore, options?: KeyframeStoreOptions) => KeyframeStore;
```

The lineage anchor is the caller's state rather than the store's, which is what keeps the store free of any notion of a lineage at all. A caller holds one hash per history and updates it whenever a write comes back with an empty base.

## Tests

Colocated beside each source file ([testing](/docs/architecture/server-testing)), against an in-memory backend, with the corpus built at describe scope:

- A keyframe and a delta each round-trip to the exact input bytes.
- Writing the same plaintext twice writes one object, and the second write reports itself deduplicated with no stored bytes.
- A small edit encodes as a delta; a wholesale rewrite promotes to a keyframe. Both are asserted through the reported base rather than through object internals.
- A document large enough to need a wide window decodes, which is the regression test for the window being recorded in the header rather than assumed by the decoder.
- A truncated or altered object fails the read instead of returning bytes that do not hash to the key.
- Collection keeps an object still named as a base by a surviving row, and deletes one nothing names.
- A keyframe is durable before any delta naming it, asserted by the order of backend calls.

One test is the value proposition itself: **the total stored bytes for a fixed corpus, as an inline snapshot.** Compression ratios are not speed, so the benchmark cannot gate them, and a regression that quietly turned every version into a keyframe would otherwise pass every test above. The snapshot is deterministic because the corpus and the parameters are.

The package carries the bundle-size snapshot every published package does.

## Benchmarks

Colocated `*.bench.ts`, against the in-memory backend so the measurement is the codec, with the colocated report committed and diffed like every other benchmark in the repo. Grouping follows the rule that a benchmark comparing shapes must fix the scale, so each document size is its own inner describe and the tasks inside it differ only in what is being encoded:

- **Baseline task named for the current behaviour** — writing the plaintext straight to the backend, which is exactly what a revision costs today. Every other task in the group is then reported against the thing this proposal replaces, which is the comparison worth having.
- **Write tasks** — deduplicated, delta, and promoted, so the three paths a write can take are each visible.
- **Read tasks** — a keyframe and a delta, against reading a raw copy, so the cost of the second fetch and the extra decompression is stated rather than assumed.
- **Shape variation within each scale** — a single-cell edit, a broad edit, a wholesale rewrite, and an incompressible payload. The last is the honest worst case: content that cannot be compressed or differenced promotes every time, and the benchmark should show what that costs rather than only reporting the flattering corpus.

Fixtures are built at module scope, which is safe here because nothing the store does mutates its input. The parameters are options rather than constants precisely so a sweep of level and window can run as a benchmark group without touching the implementation.

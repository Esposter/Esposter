# Settings surfaces (room + user settings dialogs)

Read when adding a tab, panel or field to the room or user settings dialog. Both dialogs share one structure and these conventions — apply them to every new settings tab or field:

- **Panels are lazy + skeletoned.** Each tab is a `defineAsyncComponent` in `SettingsContentMap` (room) / `UserSettingsContentMap` (user); the shared `Content.vue` of both dialogs (`apps/web/app/components/Message/Model/Room/Settings/Content.vue`, `apps/web/app/components/Message/Model/User/Settings/Content.vue`) wraps `<component :is>` in `<Suspense :timeout="0">` with `<MessageModelSettingsSkeleton />` as the fallback. New tabs get the skeleton for free — never add per-panel spinners; if a panel needs data, top-level `await` it and let Suspense show the skeleton. The exception is a panel that reads a store ref which can stay undefined, such as `userSettings`: the Notifications and Voice user-settings panels keep a per-panel `v-else` to `<MessageModelSettingsSkeleton />` on that ref, because a top-level `await` would turn a failed read into a blank panel.
- **A settings write is an overlay entry where a held row exists, and an awaited write where none does.** A write over a row the overlay holds is sent with `writeOptimistic`, as the user settings store does (`apps/web/app/store/message/user/settings/index.ts`): the entry shows the value at once, a refused write drops it and surfaces the error, and the answer's row, at its version, confirms it. The version gate means a slow earlier answer never clobbers a newer one. The rules are `openspec/changes/architecture-optimistic-overlay/design.md`. Where no store holds the row, the write is an awaited `executeMutation` with `awaitedBecause` naming its reason, and the control waits on it: the room's word filter form (`apps/web/app/components/Message/Model/Room/Settings/Type/WordFilter/Form.vue`) is one, since no store holds a filter row. It names `AwaitedReason.ServerDecidedOutcome`, because the server merges other moderators' words into the list and decides what is saved.
- **Sidebar section highlight is `useVisibleSectionIds`; the list draws it.** The composable is passed the panel's section ids and the scroll container's id, and every id it returns is active at once. A page's sidebar (`apps/web/app/components/User/Settings/SideBar.vue`) draws it as a `StyledSlideIndicator` rail over items carrying `data-slide-indicator-key`. A settings dialog's sidebar draws no rail: its list is a `UiList` whose rows take `isCurrent` from the visible ids, the UI library's own current-row primitive. Never hand-roll a sliding rail, a scroll handler, or a flag pinning the highlight during a programmatic scroll — the highlight follows the content, so there is nothing for a click to disagree with. `openspec/specs/architecture/section-navigation/design.md` owns it.

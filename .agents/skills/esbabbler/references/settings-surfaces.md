# Settings surfaces (room + user settings dialogs)

Read when adding a tab, panel or field to the room or user settings dialog. Both dialogs share one structure and these conventions — apply them to every new settings tab or field:

- **Panels are lazy + skeletoned.** Each tab is a `defineAsyncComponent` in `SettingsContentMap` (room) / `UserSettingsContentMap` (user); the shared `Content.vue` of both dialogs (`apps/web/app/components/Message/Model/Room/Settings/Content.vue`, `apps/web/app/components/Message/Model/User/Settings/Content.vue`) wraps `<component :is>` in `<Suspense :timeout="0">` with `<MessageModelSettingsSkeleton />` as the fallback. New tabs get the skeleton for free — never add per-panel spinners; if a panel needs data, top-level `await` it and let Suspense show the skeleton.
- **Every settings mutation is optimistic.** Never make a control wait on the server round-trip. A settings write is an overlay entry over its row, sent with `writeOptimistic` as the user settings store does (`apps/web/app/store/message/user/settings/index.ts`): the entry shows the value at once, a refused write drops it and surfaces the error, and the answer's row, at its version, confirms it. The version gate means a slow earlier answer never clobbers a newer one. The rules are `openspec/changes/architecture-optimistic-overlay/design.md`.
- **Sidebar section highlight is `useVisibleSectionIds` feeding `StyledSlideIndicator`.** Items carry `data-slide-indicator-key`, the composable is passed the panel's section ids and the scroll container's id, and every id it returns is active at once so the rail stretches across them. Never hand-roll a sliding rail, a scroll handler, or a flag pinning the highlight during a programmatic scroll — the highlight follows the content, so there is nothing for a click to disagree with. `openspec/specs/architecture/section-navigation/design.md` owns it.

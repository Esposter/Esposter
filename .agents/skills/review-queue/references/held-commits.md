# Held Commits and the Collector's Issues

Read when the collector opens an issue — commits parked on an `ai/held/*` branch, a window's deferred findings, or a red `main` past its repairs — or when a collector run is red, or a window was cut again.

The collector routes around what a session could not finish past its attempts rather than stopping on it, and hands the residue to the tracker: one issue per park, one per window's deferred findings and one per failure signature the repairer gave up on, each labelled `ready-for-agent` and carrying the steps that finish it. None of them holds the queue, so each is work like any other issue, never an outage.

**When an issue names commits parked on `ai/held/<short-sha>`** — the sync's resolver, the reshaper or the fold failed on them past the attempt cap, the express lane's cut never applied them at the cap's worth of `main` heads, the port still could not take the first one, or a session pushed them to the queue while the sync rewrote it and they conflict with the rewrite, and the issue's first line says which — the queue has already moved on without them. Each commit is on its own held branch before anything dropped it, and the held branch takes it out of what the queue owes, so no replay meets it again. Re-land them on `ai/queue` as the issue lists them: `git fetch origin`, then for each held branch in order `git cherry-pick --no-commit origin/ai/held/<short-sha>` and settle what the cause names: a commit too big for the window is split under the cap with the parts that need no review trailered `Express:`, a conflict is resolved against the tree the queue now sits on, and a claimed commit the express lane never applied is re-landed without its `Express:` trailer. Commit each part under a message of its own, `git commit -m "<subject>"` — never the message the pick prepares, nor `-x`: either can carry a "(cherry picked from commit …)" line naming a sha the held branch carries, and a commit whose body names one is subtracted from what the queue owes until that branch is deleted. Then `pnpm ai:queue:push`, then `git push origin --delete ai/held/<short-sha>` for each and close the issue. Being a new commit, the re-landing ports as any queue commit does, with no attempt counted against it. A parked fix — a commit carrying `Answers:` or `Drains:` from `ai/review-fixes` — needs no re-land: the finding it answered reads as open again and the next drain fixes it afresh, so its held branch is deleted once that fix is on `develop`. Every count names the collector's own services (`COLLECTOR_SOURCE_PATH`) as its basis, so a cause that is the collector's fault is fixed there first (`apps/web/content/docs/infra/review-collector/runner.md`).

**When an issue lists a window's deferred findings** — the drain failed past the cap, so each open finding got a `Deferred after <n> attempts` reply and the walk went on — nothing waits on it, and the findings are the session's to answer like any other: fix each in a commit carrying `Answers: <comment id>` (`Drains: <review id>` for the body's), reject the rest by reply with the evidence, push, and close the issue once every finding it lists is answered (`references/answering-findings.md`). The cause the issue quotes says whether the collector failed rather than the findings: a collector fault is answered by fixing the collector's services on `ai/queue`, which every later drain runs on.

**When an issue names a red `main` past its repairs** — the same workflow's same jobs failed the repairer past the attempt cap within `REPAIR_SIGNATURE_SPAN_MS` — the repairer has stopped on that signature, and nothing else waits. Reproduce the failing jobs as CI runs them, commit the repair on `ai/queue` carrying `Express:` so the lane cuts it to `main` unread, and close the issue once `main` is green; the repairer takes the signature up again on its own once its oldest attempt ages out of the span, or the collector's services change.

**When a window was cut again** — its pull request closed with a comment naming the smaller cap its replacement is cut to — nothing is owed: the bot skipped its review past the collector's asks, the collector closed it and every window above it, and the opener has already cut their commits anew. A window that keeps coming back smaller is the CodeRabbit plan or its billing refusing reviews — a file limit under the one `REVIEW_FILE_CAP` names, or usage credits run out — and only a person fixes that; once fixed, the next window is reviewed and the cap returns to the plan's.

**When a collector run is red** — what no run can route around: fixes too many for the cap on their own, an open window whose base is not the window below it, or an error in the collector's own code. The run's error names which and what it read. An error in the collector is fixed in its services on `ai/queue`, and the push runs the cycle again; a broken chain is a window a person retargeted or reopened out of order, put back on the window below it.

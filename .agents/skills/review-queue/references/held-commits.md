# Held Commits and the Collector's Issues

Read when the collector opens an issue — commits parked on an `ai/held/*` branch, a window's deferred findings, or a red `main` past its repairs — or when a collector run is red, or a window was cut again.

The collector routes around what a session could not finish past its attempts rather than stopping on it, and hands the residue to the tracker: one issue per park, one per window's deferred findings, one per failure signature the repairer gave up on and one per red the newest collector runs keep failing on, each labelled `ready-for-agent` and carrying the steps that finish it. None of them holds the queue, so each is work like any other issue, never an outage.

**When an issue names commits parked on `ai/held/<short-sha>`** — the sync's resolver, the reshaper or the fold failed on them past the attempt cap, the express lane's cut never applied them at the cap's worth of `main` heads, the port still could not take the first one, or a session pushed them to the queue while the sync rewrote it and they conflict with the rewrite, and the issue's first line says which — the queue has already moved on without them. Each commit is on its own held branch before anything dropped it, and the held branch takes it out of what the queue owes, so no replay meets it again. The collector re-lands each itself, on the run after the park and then once per `main` head ("When a held branch is gone", on this page); to re-land one by hand, do it on `ai/queue` as the issue lists them: `git fetch origin`, then for each held branch in order `git cherry-pick --no-commit origin/ai/held/<short-sha>` and settle what the cause names: a commit too big for the window is split under the cap with the parts that need no review trailered `Express:`, a conflict is resolved against the tree the queue now sits on, and a claimed commit the express lane never applied is re-landed without its `Express:` trailer. Commit each part under a message of its own, `git commit -m "<subject>"` — never the message the pick prepares, nor `-x`: either can carry a "(cherry picked from commit …)" line naming a sha the held branch carries, and a commit whose body names one is subtracted from what the queue owes until that branch is deleted. Then `pnpm ai:queue:push`, then `git push origin --delete ai/held/<short-sha>` for each and close the issue. Being a new commit, the re-landing ports as any queue commit does, with no attempt counted against it. A parked fix — a commit carrying `Answers:` or `Drains:` from `ai/review-fixes` — needs no re-land by hand either: the collector re-lands it as it does any held commit and replies for it on the merged window whose finding it answers, and while that window is still the newest its finding reads as open again, so a drain that fixes it afresh first leaves the re-land a pick the queue already carries. A drain that writes a fix alone over the cap again has that attempt counted, so past the cap the finding is deferred rather than fixed afresh without end. Every count names the collector's own services (`COLLECTOR_SOURCE_PATH`) as its basis, so a cause that is the collector's fault is fixed there first (`apps/web/content/docs/infra/review-collector/runner.md`).

**When an issue lists a window's deferred findings** — the drain failed past the cap, so each open finding got a `Deferred after <n> attempts` reply and the walk went on — nothing waits on it, and the findings are the session's to answer like any other: fix each in a commit carrying `Answers: <comment id>` (`Drains: <review id>` for the body's), reject the rest by reply with the evidence, push, and close the issue once every finding it lists is answered (`references/answering-findings.md`). The cause the issue quotes says whether the collector failed rather than the findings: a collector fault is answered by fixing the collector's services on `ai/queue`, which every later drain runs on.

**When an issue names a red `main` past its repairs** — the same workflow's same jobs failed the repairer past the attempt cap within `REPAIR_SIGNATURE_SPAN_MS` — the repairer has stopped on that signature, and nothing else waits. Reproduce the failing jobs as CI runs them, commit the repair on `ai/queue` carrying `Express:` so the lane cuts it to `main` unread, and close the issue once `main` is green; the repairer takes the signature up again on its own once its oldest attempt ages out of the span, or the collector's services change.

**When a held branch is gone and its issue closed on its own** — the collector re-landed the commit, and nothing is owed. After the openings each run picks every held commit onto `ai/queue`'s head once per `main` head — the head it was parked at included, tried by the run after the one that first found it held, which wakes for it — a conflict going to the sync's resolver, commits the copy under a message of its own with a `Relanded:` trailer naming the held commit, pushes it, deletes the branch and closes the issue once every branch it lists is gone; a re-landed fix is replied for on the merged window whose finding it answers. An `Express:` commit parked while no window was open is still part of `ai/queue`'s history, and its copy is picked only once the queue's next rewrite drops it. A commit it stopped trying — past its attempts, parked again as often as it was re-landed, or alone over the plan's cap — stays the session's to re-land by hand as the issue lists (`apps/web/content/docs/infra/review-collector/collection-cycle.md`, "Re-land").

**When a window was cut again** — its pull request closed with a comment naming the smaller cap its replacement is cut to — nothing is owed: the bot skipped its review past the collector's asks, or the window sat off the stack's chain of bases, the collector closed it and every window above it, and the opener has already cut their commits anew. A release from `develop` the bot kept skipping is closed the same way, its branch kept, and its commits cut into windows. A window that keeps coming back smaller is the CodeRabbit plan or its billing refusing reviews — a file limit under the one `REVIEW_FILE_CAP` names, or usage credits run out — and only a person fixes that; once fixed, the next window is reviewed and the cap returns to the plan's.

**When a collector run is red** — what no run can route around: an error in the collector's own code. The run's error names which and what it read, and stands as the job's annotation. The guard wakes the cycle five minutes after a red, until the newest runs fail alike — the same step, the same error line — `GUARD_RED_STREAK` times in a row: then it opens one issue titled `Collector red: <step>: <line>` instead and wakes nothing, and the next push or event wakes the cycle as usual. An error in the collector is fixed in its services on `ai/queue`, and the push runs the cycle again.

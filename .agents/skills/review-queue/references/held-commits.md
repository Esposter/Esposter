# Held Commits and the Collector's Issues

Read when the collector opens an issue — commits parked on an `ai/held/*` branch, or a window's deferred findings — or when a collector run is red.

The collector routes around what a session could not finish past its attempts rather than stopping on it, and hands the residue to the tracker: one issue per park and one per window's deferred findings, each labelled `ready-for-agent` and carrying the steps that finish it. None of them holds the queue, so each is work like any other issue, never an outage.

**When an issue names commits parked on `ai/held/<short-sha>`** — the sync's resolver, the reshaper or the fold failed on them past the attempt cap, or the port still could not take the first one, and the issue's first line says which — the queue has already moved on without them. Each commit is on its own held branch before anything dropped it, and the held branch takes it out of what the queue owes, so no replay meets it again. Re-land them on `ai/queue` as the issue lists them: `git fetch origin`, then for each held branch in order `git cherry-pick --no-commit origin/ai/held/<short-sha>` — without `-x`, because a copy whose body names the held sha is subtracted from what the queue owes and would never port — and settle what the cause names: a commit too big for the window is split under the cap with the parts that need no review trailered `Express:`, and a conflict is resolved against the tree the queue now sits on. Commit, `pnpm ai:queue:push`, then `git push origin --delete ai/held/<short-sha>` for each and close the issue. Being a new commit, the re-landing ports as any queue commit does, with no attempt counted against it. A parked fix — a commit carrying `Answers:` or `Drains:` from `ai/review-fixes` — needs no re-land: the finding it answered reads as open again and the next drain fixes it afresh, so its held branch is deleted once that fix is on `develop`. Every count names the collector's own services (`COLLECTOR_SOURCE_PATH`) as its basis, so a cause that is the collector's fault is fixed there first (`apps/web/content/docs/infra/review-collector/runner.md`).

**When an issue lists a window's deferred findings** — the drain failed past the cap, so each open finding got a `Deferred after <n> attempts` reply and the walk went on — nothing waits on it, and the findings are the session's to answer like any other: fix each in a commit carrying `Answers: <comment id>` (`Drains: <review id>` for the body's), reject the rest by reply with the evidence, push, and close the issue once every finding it lists is answered (`references/answering-findings.md`). The cause the issue quotes says whether the collector failed rather than the findings: a collector fault is answered by fixing the collector's services on `ai/queue`, which every later drain runs on.

**When the red names a window still skipped after the collector's one ask for its review** — the run's error says "the bot skipped its review again after it was asked" — the CodeRabbit plan or its billing is refusing it: a file limit under the cap the collector cuts to, or usage credits run out. Fix the plan or the billing first, then comment `@coderabbitai review` on that window; the bot's reply fires the cycle, which merges the window once its review completes. The collector never asks twice on its own, since a second ask before the fix is skipped the same way.

# Row Versions and Tombstones

Read when adding a table the client holds through the overlay, adding a column to such a table, or writing a delete or a revival. `SKILL.md` states each rule in one line, and this page carries the full statement of each. The reasoning is in the change design's Database section, `openspec/changes/architecture-optimistic-overlay/design.md`, until that change is archived.

- **Every table carries `version`.** `createVersionSchema()` (`packages/db-schema/src/createMetadataSchema.ts`) is spread by `createMetadataSchema()`, which every D1 table takes, and directly by each object's tables in `packages/db-schema/src/objects/*/schema.ts`. The migration that adds the column makes it `NOT NULL DEFAULT 0`, and that default is the value an insert takes. It is not a fill for missing data, so it is not a backfill (`references/migrations.md`).
- **The database raises `version`, and no writer names it.** The column's `$onUpdateFn` is embedded in the statement as SQL, so each update adds one in the same statement it runs. A write that names a version could lower it, so no caller sets one.
- **A row's identity is its primary key.** An optimistic entry addresses a row by that key, one level per column of a composite, and never by a string built from the columns. Keep a tracked table's primary key a stable identity: changing it changes which rows an entry touches.
- **A removal is a soft delete that leaves a tombstone.** The row keeps its place, `deletedAt` is set, and `version` is raised, so an older arrival for its key loses. A row the overlay holds is never hard-deleted. The one hard delete is the purge's, which removes a tombstone once it is past `TOMBSTONE_RETENTION_MS`.
- **A revival is an upsert.** A re-created key is written with `INSERT … ON CONFLICT` whose conflict branch clears `deletedAt`, so the row keeps counting above its tombstone. A revival's `where` names only tombstones, so a set-where over a live row leaves it alone.
- **Every decision about live rows takes `getLiveRowWhere`.** Server guards, counts and reads filter on `getLiveRowWhere` (`packages/db-schema/src/services/tombstone/getLiveRowWhere.ts`). A read the overlay holds returns its tombstones within its scope, so a removal reaches the client as a row, and the view hides it.
- **A table whose tombstones the purge removes is listed.** `OVERLAY_TOMBSTONE_TABLES` (`packages/db-schema/src/services/tombstone/constants.ts`) names the tables the nightly purge removes tombstones from, past `TOMBSTONE_RETENTION_MS`. The table also gets `createTombstoneIndex` (`references/indexes.md`). `apps/web/server/db/overlayTombstoneTables.test.ts` fails when a soft-delete statement names a table the list does not. An object's tombstones are purged by its own alarm (`references/durable-object-schemas.md`).
- **No raw statement writes a tracked table.** A raw `UPDATE` skips the Drizzle builder, so it skips the increment, and every write routes through the builder.
- **A version a writer sets is rejected.** The database raises the version, so no writer ever names one, and a trigger is kept only as the fallback for a raw write path the builder does not cover.

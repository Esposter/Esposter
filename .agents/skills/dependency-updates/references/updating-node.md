# Updating node

Read when the node version moves. This page holds the whole procedure; `SKILL.md` keeps the one line that node moves as one group and is never hand-edited.

The node version is one pin, `.node-version`, and two things write it, and both also move the `@types/node` catalog entry. The bot's `node` group bumps the pair in one branch (`references/renovate.md`) — a minor or patch merges on green, a major opens a PR for a person; after pulling either, run `pnpm update:node` with no argument so the machine catches up — step 3 below, since `.node-version` already carries the version. Ahead of the bot, `pnpm update:node [version]` from the repo root is the same write by hand. With no argument it targets `latest`, the Current line rather than LTS, which is the line Renovate's `node` rule tracks too (`references/renovate.md`). In one call it:

1. Pins through `vp env pin <version> --target node-version --force` — vp resolves a whole or partial request to its highest release (`24` becomes `24.x.y`), `latest` (the default) is the Current line rather than LTS, and the pin writes `.node-version` and installs it, which is what `pnpm/setup` installs on the runners. The script never reads nodejs.org or the npm `node` package itself, whose `latest` tag is a third party's and lags the real line
2. Bumps the `@types/node` catalog entry to the highest release matching the new node major, when the pin changed. Then moves every manifest's node floor to `>=` the new version with the pin: `engines.node`, and the `node` entry of `devEngines.runtime` in either its object or its array form, in every workspace `package.json` that carries one (a plugin's copy included). Each `package-lock.json` beside one has its root entry's `engines.node` moved the same way. Only the changed files are written, one `✔` line each. The floors run on an unchanged pin too, so a floor Renovate's pin-only branch left behind is caught up
3. Runs `vp env clean`, which removes the versions no pin or default names any more. `vp` resolves node and the pnpm `packageManager` per directory through shims that stand in for Corepack, so nothing is defaulted or switched. `vp env` exists only in the global CLI (`https://viteplus.dev/guide/`), never the `vite-plus` copy the install lays down, so a machine without it fails here by name

The TS orchestration (`scripts/src/updateNode/`) runs the `vp env` pin and clean, then edits the manifests and lockfiles the pin moves. The pure manifest and lockfile editors and the `@types/node` registry read live under `scripts/src/services/updateNode/` with unit tests; the generic registry/version utilities live in `scripts/src/services/shared/`.

It deliberately does **not** refresh the lockfile. After it finishes, run `pnpm refresh:lockfile` to resolve the new `@types/node`. Already-open shells keep the old version until reopened.

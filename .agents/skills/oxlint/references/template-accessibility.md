# Template Accessibility — vize's `a11y/*` rules

Read when an `a11y/*` rule reports on an SFC template, when adding an accessibility attribute or role to one, or when deciding whether one of the staged-off rules is ready to promote. This page holds the whole rule; `SKILL.md` keeps the directive syntax.

SFC templates are linted by vize's `a11y/*` rules, configured in `vite/vueOptions.ts` and run by the root `lint:vue` task, which reads each whole component, so it costs nothing type-aware and covers the app and the packages alike.

- **A staged-off rule carries its promotion condition beside it** in `vite/vueOptions.ts`. The keyboard-interaction ones are satisfied by adding tab stops, widget roles and focus-driven reveals — keyboard design decisions (a list of clickable cells wants one roving tabindex, not one tab stop each), not markup fixes. Promote a rule together with the widget pattern that earns it, never to quiet a lint run.
- **The adopted accessibility surface is what these rules check, and nothing beyond it.** A rule catches attributes, roles and handlers on an element; it cannot see page structure. So heading-level semantics — "the page title should be an `<h1>`", "sections want `<h2>`" — are **not** a convention here, and a review finding asking for one is declined rather than applied. Visual role is carried by one of the library's type rules (`ui-heading`, `ui-title`) on whatever element the layout wants, and titles usually come from a shell primitive (a layout's page header) rather than page markup, so no page can decide its own level correctly anyway. An unenforceable rule buys drift, not accessibility.
- **A finding on a component tag is usually wrong.** Most interactive markup here is the UI library's components, which the plugin sees as an opaque tag and either skips or judges by a prop it can't resolve; a Vue component nested inside `<svg>` is misread as a plain element outright. Reach for the rule's own option before a disable — several ship an escape hatch as an option. `no-autofocus` is off for that reason: it sees only a DOM element's attribute, and a library component forwards one, so the selector list in `scripts/src/services/oxlint/selectorBan/syntaxes/restrictedSyntaxes.ts` bans `autofocus` on any element or component, and as an object key, in its place (the `ui-library` skill, `references/fields.md`).
- **Never silence a finding with an `aria-label` restating visible text.** Fix the markup, or disable the line with the reason. A control that only proxies a labelled affordance (a `hidden` file input behind a button) is `aria-hidden="true"` **plus** `tabindex="-1"`; `aria-hidden` alone trips `no-aria-hidden-on-focusable`.
- **`aria-hidden` never sits on anything a click can focus.** `no-aria-hidden-on-focusable` counts `tabindex="-1"` as focusable, since it only leaves the tab order: a click still focuses the element, and the browser then drops the `aria-hidden` with a console error. So the pair is honest only beside `hidden`, which the rule reads, so the hidden file input needs no disable. A pointer-only duplicate — an avatar linking where the name beside it already does — keeps `tabindex="-1"`, drops `aria-hidden`, and carries the name as its `aria-label`, so a screen reader meets a named link rather than an empty one. `inert` is no way out: it blocks the click as well.
- **Template directives are HTML comments**: `<!-- oxlint-disable-next-line a11y/<rule> -- reason -->`. `-next-line` reaches the element's opening line only, so an attribute several lines down a multi-line tag needs an `oxlint-disable` / `oxlint-enable` pair wrapping the element instead. Both forms are safe above a single root element: the dev-mode render function becomes a fragment carrying `DEV_ROOT_FRAGMENT`, which the runtime resolves back to the one-element child for attribute fallthrough, and the production compiler strips template comments outright.

# A Shared Checkout

Read when another session shares the checkout: committing by pathspec, a file both sessions edited, amending, and naming a commit to reset to.

- **Commit by pathspec when another session shares the checkout** — `git commit -F - -- <your paths>`. The index is shared: a rename or edit the other session already staged rides into a plain `git commit` even when only your files were `git add`ed, and staging yours does not unstage theirs. A pathspec commit takes only the paths named and leaves the rest of the index as it was; an `R`, `M` or `A` in `git status --short` on a file you did not touch is the tell that the index is not yours. Its pre-commit hook runs against a temporary index, so the formatting it stages reaches the commit but not the shared index, and `.githooks/post-commit` resets each committed file's stale entry to `HEAD`; an `MM` on a file you just committed means that hook did not run (`pnpm i` sets `core.hooksPath`), and `git reset -q -- <path>` clears it. **A file both sessions have edited cannot be committed by pathspec at all**: the pre-commit format hook restages the whole file, so the other session's hunks ride out under your message. Save their copy aside, write the file as `HEAD` plus your change alone, commit, then put their copy back. So the edit is what to avoid: **a file `git status --short` already lists as modified is the other session's mid-edit, and an edit landed on top of it rides out under whichever session commits the file first** — read the status for a file before touching it, and leave a listed one until it is committed. **`git commit --amend` takes no pathspec** — it recommits the whole index, so amending a pathspec commit to fix its message pulls in everything the other session has staged since. Reach the message with `git reset --soft <your sha>~1` and a fresh pathspec commit, which leaves their staging where it was. **Name your commit by its sha, never by position** — `git reset --soft <your sha>~1` — since the other session's commit can land on top between reading `git log` and the reset, and `HEAD~1` then undoes theirs.
- **A commit of a shared file can carry a hunk that imports a file no one committed.** The pre-commit hook does not check imports, so the commit lands. The push's typecheck is where it shows, since the checkout built from that commit cannot resolve the module. Fix it in a commit behind the push that `git add`s the missing file, or leave that hunk out of this one.
- **Committing only your hunks of a file a peer also has dirty.** A pathspec commit takes the whole working file, peer's hunks included. So build the commit in a throwaway detached worktree cut from the branch head, with your hunks applied there, and record that head. Then move the branch with a compare-and-swap, `git update-ref refs/heads/ai/queue <new> <recorded head>`: it refuses if anyone committed meanwhile, where a plain `update-ref` or `reset` silently drops their commit. Last, run `git restore --staged <file>` in the checkout, so its index matches the new head and no reversal of your hunk sits staged for the next plain commit.
- **A throwaway worktree has no `node_modules` of its own, so its pre-commit format runs on the main checkout's tools.** The hook borrows the main checkout's `oxfmt` and config when the worktree has none (`.githooks/pre-commit`), so a `git commit` there formats; a commit that skips the hook keeps the files as they were written. Format the files first with the checkout's own `node_modules/.bin/oxfmt`, then copy them in. A compare-and-swap that refuses leaves its commit dangling: rebuild on the new head rather than moving the branch by hand, and check the commit's stat for a blank line where a row belongs, since a `grep` feeding the row can come back empty while a peer rewrites the file.

# Test Helper Files

Read when a helper, a fixture or a hook block is shared between suites, or a helper-only `.test.ts` or `.bench.ts` is being written.

## Test utility files

Shared test helpers live in `.test.ts` files (and bench helpers in `.bench.ts`) — both suffixes are excluded from the published barrel by `ctix` and from the `tsc` build, so they never ship. The file-organisation rules apply unchanged: **one function per file, named after the function**, never a `testUtils`-style grab-bag.

- **A helper only one suite calls has no file of its own — it lives in that suite.** A production `.ts` for code nothing in production imports is shipped build output serving one caller, and the `.test.ts` split only earns its place once a second suite imports it. Module scope in the test file is the right home (a pure function is explicitly allowed there), and the move to its own `.test.ts` happens when the second consumer appears, not in anticipation of one.
- **One helper function per file** — `createRow.test.ts` exports only `createRow`, `createWorkspaceCorpus.test.ts` only `createWorkspaceCorpus`. Follow the `create*` prefix convention for factories/builders. Cross-helper reuse is a normal import (`setupWithDataSource.test.ts` imports `createDataSource.test`).
- **Shared constants/fixtures go in `constants.test.ts` / `constants.bench.ts`** — the test/bench equivalent of the `constants.ts` exception (see the `file-organization` skill). Group module-level fixture data here (e.g. derived bench data sources) instead of one trivial file per constant. A seed constant that a helper function is built around may colocate with that function when grouping it in `constants.*` would create a circular import (the derived fixtures call the generator at module init).
- **`describe.todo` placeholder** — every helper-only `.test.ts` ends with `describe.todo("<fileName>")` (the function/file name, e.g. `describe.todo("createRow")`) so Vitest accepts the file without a real suite. **A helper `.bench.ts` ends with the same placeholder** — Vitest collects a `*.bench.ts` as a spec of its own and fails it with `No test suite found in file` when it declares no `bench()`, which is a red 🏎️ Bench run for a file that was never meant to measure anything. The todo suite costs no artifact: the reporter drops a group with no benchmarks, so the helper writes no `*.bench.md` and the files importing it render no extra section.
- **`setup*` fixture helpers for repeated hook blocks** — when 2+ suites copy-paste the same `beforeEach`/`afterEach` (or `beforeAll`/`afterAll`) block, extract a `setup*` helper (`setupTemporaryCacheHome.test.ts`, `setupWarmSnapshotSuite.test.ts`, app's `setupWithDataSource`, the router suites' `setupRoomSuite`) that **registers the hooks itself** at the top of `describe` and returns getters for the state it owns (`getCacheHome()`, `getBackend()`). Suite-specific extra hooks stay in the suite — Vitest runs before-hooks in registration order (fixture's first) and after-hooks in reverse, so they compose. The file needs the usual `describe.todo`. When a getter's value is used many times per test (a caller, a per-test `roomId`), the suite aliases it into a local `let` in its own `beforeAll`/`beforeEach` rather than calling the getter at every use. When every consumer would write the same tests over those getters — the eight oxlint plugin suites each asked one fixture-count matrix and one "nothing but these rules" check — the helper registers the tests too and returns nothing (`setupPluginSuite`): the suite is then its fixture table and one call, and a getter with no consumer is not exported.
- **A fixture that spawns to build is built once per file and copied per test** — when the per-test state is a directory a process tree builds (`setupFixtureRepository.test.ts`: a bare origin and a clone, a dozen git spawns), the helper builds it in `beforeAll` into a template directory and `cpSync`s the template in `beforeEach`; the copy is a file walk where the build is process creation, which is what a spawn costs on Windows. Isolation is unchanged — every test still owns its own copy — and anything the copy must keep pointing at itself (a git remote) is recorded as a path relative to the copy. A stub the config clears after every test (`unstubEnvs`) is stubbed in both hooks, since the template build runs under it too.

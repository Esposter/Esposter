# Client-Side tRPC Calls

Read when a component or store under test calls a tRPC procedure from the client.

Call `setupMswTrpc()` at `describe` scope (`@/services/trpc/mswTrpc.test`) and register per-test resolvers on `trpcMsw`: `trpcMsw.foo.createFoo.mutation(({ input }) => …)`. Resolvers are typed off `TRPCRouter`, so a renamed or re-shaped procedure fails to compile instead of silently answering a call that no longer exists — the thing a hand-written client stub cannot do. The real plugin, links and transformer all run, and the mock router answers with the server's own `rootConfig`, so a thrown `TRPCError` reaches the store exactly as a real rejection does. **Never `vi.mock` the tRPC client.** How the package answers a call is `apps/web/content/docs/trpc-msw/index.md`.

- A resolver receives tRPC's own resolver options — `ctx`, `input`, `path`, `signal` — so a spy's recorded call is read as `takeOne(resolver.mock.calls)[0].input`.
- **Every call first passes the real procedure's input parsers**, since `setupMswTrpc` hands `trpcRouter` to the mock, so a call the server would reject rejects with its `BAD_REQUEST` before the resolver runs. A suite that fails there is sending a value no production caller can send — a uuid where the schema takes a rowKey or a call id, an empty key, a name that trims to nothing — and the value is what changes, to the one the `test-values` skill names for that kind, unless production code can send it too, which makes the failure a bug and the test its regression.
- A procedure with no resolver registered rejects with `NOT_FOUND` rather than reaching the network, so a test that forgets one fails on the call it forgot. Plain `http.*` handlers still go on the returned server with `server.use`, and a non-tRPC request with no handler passes through.
- The client runs its production links under test — batching included — because in the browser the module's links send through the global `fetch` against an absolute url (`apps/web/content/docs/trpc-nuxt-module/index.md`). Calls issued in the same tick therefore share one batched request, which answers only once every call in it settles: a test that holds one call open while another must settle first issues the second only after the held one has reached its resolver, as two overlapping writes are two requests in production.
- **A test fails when a request goes out after it ended.** `setupMswTrpc`'s `afterEach` first lets msw answer every request already in flight, then waits one timer boundary, then fails with the url of every request sent since the test ended. Usually this is a click handler's last call, such as a re-read after the effect the test awaited. Just as often it is the very request the test is about: a batch leaves a timer turn after the call, so a rejection, a rollback or a gated read the test asserts on may never reach msw at all, and the test passes without exercising it. Left alone, that request lands after msw closes, and its log races the worker's teardown into an intermittent `EnvironmentTeardownError: Closing rpc while "onUserConsoleLog" was pending`, reported against whichever file happened to be running. The fix is to await the call that is still out: its resolver resolves a promise as the request reaches it, and the test awaits that and flushes once. Do not await an earlier effect and let the rest of the chain run on.
- A call msw misses fails with `fetch failed`, because the nuxt environment's origin is a `.test` host that never resolves (`apps/web/content/docs/architecture/test-harness-workarounds.md`). A suite that fails only while a dev server runs, answered with the real router's `UNAUTHORIZED` from `.nuxt/dev`, is a request reaching the network — and instrumenting it hides it, since a log line or an extra hook moves the timing enough for msw to win. Read what msw saw through its lifecycle events pushed to an array and printed in an `afterAll`, which perturbs least.

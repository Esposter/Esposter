# Bundle Size Snapshots

Read when a package's `index.test.ts` size snapshot fails, a change moved bytes into a bundle, or a new library package needs its size test.

Every library package under `packages/` has `src/index.test.ts` asserting two `getFileSizeReport` snapshots — bundle size (`dist/index.js`) and types size (`dist/index.d.ts`), with `getFileSizeReport` imported from `@esposter/configuration`. **Copy the file from any sibling package** rather than writing it from scratch.

- **Workflow**: create with **empty** snapshots (`toMatchInlineSnapshot()`), then `pnpm build` (the test reads compiled `dist/`) + `pnpm test --run -u src/index.test.ts` to fill them in. Re-run `-u` after any later build change.
- **Refreshing several packages at once** (a change rippled through `dist/` and CI is red on the snapshots): from the repo root, `pnpm build:packages` then `pnpm test:packages -u -t "size" index.test.ts` — one rebuild of every library package, then only the size tests updated. Rebuilding first is not optional: without it `-u` writes the **stale** `dist/` back into the snapshot and CI stays red against the freshly-built bytes. The counts are byte-identical between a local build and CI's on the same OS, so a snapshot filled in locally is the one that OS's CI asserts — across OSes they can drift, which is what the per-platform split below covers.
- **The `index.test.ts` argument is not optional either — it is what stops a snapshot refresh running the suite.** `-t "size"` selects which _tests_ execute, never which _files_ load: without a path argument vitest collects, transforms and imports every test file in every library package to run the handful of assertions these files hold, which is minutes of work for the seconds they actually take. The path argument is a substring match on the file path, so it keeps one `src/index.test.ts` per package — every package still refreshed — and drops everything else. Regressing the rest is CI's job, and it shards it.
- **New library package**: add a `test` script (`"test": "vitest"`) and `vitest` + `@types/node` devDeps. Never add `@vitest/coverage-v8` per-package — coverage runs only from the repo root, so the provider lives in the root `package.json` alone.
- **Default to the simple unguarded form.** Only split per-platform once you've **confirmed** the byte count differs across OSes or CI fails on the other OS — never speculatively. Fill your own OS via `-u`; take the other OS's count from the CI failure's `Received:` line rather than leaving it empty, since nothing writes a snapshot back from CI.
- **Narrow it by file, never by package.** The pair's whole value is that it covers every library package, so the
  one whose `dist/` a change rippled into cannot be the one left out. A variant narrowed by package — skipping the
  slow one, listing the ones that "obviously" moved — reports green over the package it dropped, and the drift
  surfaces on someone else's run instead. Adding or deleting a source file is enough to move a bundle, so the
  package that needs refreshing is rarely the one the change is about. Narrowing to `index.test.ts` costs no
  coverage for the same reason: every package's size test is named that, so none of them is the one left out.
- **The root refresh pair clobbers the split package's POSIX snapshot on a Windows host — revert that one hunk.** `-u` writes back every snapshot it selects, so the refresh pair and the never-`-u`-the-POSIX-case rule below collide by construction: the run rewrites the POSIX count with the locally-built Windows bytes and reports itself green. Don't drop a package from the pair to dodge it — run it over every package, then read the diff and `git checkout --` the split package's POSIX line if it moved. The tell is that hunk changing to the exact value the `bundle size (Windows)` snapshot above it already holds.
- **On a Windows host the split package's POSIX snapshot fails locally, and that is not a regression.** The runner reads `linux` while the build ran natively (`references/running-the-suite.md`), so the POSIX test is selected against a Windows-built `dist/`. The POSIX case then measures Windows bytes and is off by exactly the minifier's couple of bytes. Only the one split package can show this; read a local `bundle size (POSIX)` failure against the `bundle size (Windows)` snapshot two lines above, and if the received count matches that one, there is nothing to fix. Never `-u` it: that writes the Windows count into the POSIX snapshot and turns a local artifact into a red CI.
- **Both halves of a split can be measured locally on a Windows host — build on each side rather than waiting for CI.** The split exists because the two OSes emit different bytes, so give each snapshot a `dist/` its own OS built: `pnpm virrun -- pnpm --filter <package> build` then `pnpm virrun -- vitest run --project <package> -u -t "size" src/index.test.ts` fills the POSIX pair from a sandbox-built artifact, and `pnpm --filter <package> build` then `pnpm vitest run --project <package> -u -t "size" packages/<package>/src/index.test.ts` — vitest invoked directly, not through `virrun`, which is what makes `process.platform` read `win32` and selects the Windows tests — fills the Windows pair. Rebuild natively last so the tree is left with the `dist/` every other check assumes. Only then does the root refresh pair's POSIX hunk need reverting again, and a POSIX case that measures identical on both OSes (a bundle small enough to have no module order left to disagree about) simply reports nothing to update.

- **What makes an artifact differ across OSes is module order, not line endings.** Line endings are not the cause — both artifacts are emitted LF on both platforms. What differs is the order the two filesystems resolve a module graph in, and each artifact spends that order differently: the bundle through the minifier, which hands out two-character identifiers in module order once single characters are exhausted, and the declaration bundle through the order it concatenates and de-duplicates declarations in. Both are deterministic per platform, and both are a property of **size** — a graph small enough has no ordering left to disagree about. So only the biggest package needs the split, and it needs it for whichever of its two artifacts CI actually shows drifting. **Split each artifact on its own evidence**: a bundle that drifts does not imply its types do, and a types bundle large enough to drift will do so by a different amount, in a different direction. Never split the second one speculatively because the first one moved.

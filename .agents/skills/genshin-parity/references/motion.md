# Motion and recording

Read when the game is recorded, a timing is read off a recording, or a screen's motion is held or tested against it.

- **Motion: find, sample, then pause.** Sample a recording at 1 fps to find its events, then sample a labelled screenshot over each one by hand outside the repository (`ffmpeg -ss <seconds> -i <capture> -frames:v 1 -vf "format=rgb24,setparams=color_primaries=unknown:color_trc=unknown:colorspace=unknown" <out>.png`; FFmpeg for video, since GIF and animated WebP, which the wiki serves, are ones it cannot decode). `shoot <screen> <w> <h> --motion entry <ms…>` holds the screen's own animations as it mounts; `props` (the default) lets those finish, then sets the fixture's `motionProps` and pauses on the transitions that setting starts. Stills and the visual suite show `props` alone. The page flushes style between the entry and the props, or the browser folds both into one style change and starts no transition. After a new import, the first load of the page reloads while Vite optimises it; shoot again. A sequence of screens runs as one Web Animations timeline per screen (fades and holds as keyframe offsets, each segment's easing on its keyframe), so a held shot at any moment shows that moment; its fixture is `isMotionOnly`, since the visual suite's screenshot finishes animations. Measured timings live in the section's `constants.ts`, with how they were measured. A recording's colours read true only because `RECORD_ENCODING` converts to labelled limited-range YUV before AMF, which otherwise labels its own limited range as full and squeezes every value (white as 234); keep that conversion, and still take exact colours from a lossless still or the wiki's PNG.
- **Record the game's window only**, with `record <name> <seconds>` armed before the user starts the game: Windows Graphics Capture by executable, GPU-encoded, Matroska. Never capture a screen rectangle, which takes the desktop, the webcam and any overlay whenever the game is not in front.
- **A section of a published video is fetched with `recreation clip --directory <captures folder under PARITY_DIRECTORY> <url> --from <s> --to <s> [--name <id>]`.** yt-dlp takes the best MP4 at or under 1080 high for only that section (`--download-sections`), merged by the pinned FFmpeg, into `captures/yt-<videoId>-<name>.mp4`, and prints its path. Public clips come through `recreation clip --directory <captures folder under PARITY_DIRECTORY>`, never a disk search or an ad hoc install. A public clip's manifest row is written from its file name by `genshin:parity recordings backfill` (no bytes uploaded), and `references restore` prints the clip command to fetch each one again. A labelled screenshot of a capture is sampled by hand outside the repository, with the command in the first bullet, and its entry's `source` records the capture's own second, not the video's.
- **FFmpeg is the pinned release the tool fetches** (`FFMPEG_ARCHIVE_URL` and its SHA-256, into `FFMPEG_DIRECTORY`). To move it, bump the version and checksum together; never add an npm FFmpeg (none bundles 8 or later, which window capture needs).
- **A screen's behaviour only a browser runs is an `Index.browser.test.ts` beside it**: the Web Animations and CSS transitions a screen or the opening hands on with, played to their ends with `finish()`, with timers and frames faked for the rest and the browser's own frame kept for the events a transition sends. The browser suite (`test:visual`) runs it; the package's ordinary suite excludes it. `Game/Opening`'s test holds the opening end to end: splashes, the login's title, flight and door, the startup marks and the finish. A 3D screen's frames are real renders, so its test's timeout covers the flight.

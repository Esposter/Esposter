# Approval

Read when writing a screen's image or citing a reference for one. The one-line rules are in `SKILL.md`; this page is their reasoning.

- **An image is a snapshot, written for every screen and variant.** `genshin:parity approve` writes a screen's image as a snapshot of its current render, whether or not a reference exists and whether or not its compare clears the bar, and the suite shoots that render in the parity page's 1920 by 1080 box over a neutral backdrop. The visual suite then holds the screen to that image, so a later change shows as a number in the suite's summary, not as a stop. Nothing about an image is judged, so nothing waits on a reference for one.

- **A committed reference is the game's frame, and `approve` never writes it.** Each fixture variant's reference is a lossless WebP beside its snapshot, and the other references sit flat in `packages/genshin-world/parity/references/`; `references pack` writes them. `approve` writes only the snapshot image, from the render; it reads the committed reference for the score and stops with the path when that file is absent.

- **The score is a report.** Where a screen has a whole-screen reference on disk, `compare` and `approve` record its score in the committed report, `ParityReferenceMap.snapshot.md`, whether or not the score is under the bar. `approve` prints the score's status against the screen's bar before it writes the image: `within the bar`, `over the bar`, `no reference`, `compare failed`, or `not the whole screen`. A status is read, never a gate. The visual suites list each case over one percent of its image, worst first, after the run, and the run passes.

- **A reference is hunted once per component.** A new fixture gets a map entry with its reference, or a pending entry with the reason it has none, and `ParityReferenceMap.test.ts` fails for any non-motion fixture that no entry names. A component that already has an entry or a pending entry is never re-hunted, and never re-done, just to approve its image: `approve` takes the image from the render as it stands.

- **The order for a new screen is reference, fixture, component, `compare`, `approve`, suite.** The reference comes first because the screens built without it drifted: with the screenshot beside the screen, the parity loop has a target from the first line of the component. A fixture variant is a subscreen, and each names a reference of its own through the entry's `variant`, or a pending entry stating why it has none; `ParityReferenceMap.test.ts` fails on a variant that borrows its base's. A screen folder with no fixture is named in `packages/genshin-world/parity/pendingScreens.ts`, which `parity/screens.test.ts` reads.

- **"No reference, no approval" binds a measured value, not an image.** A screen's size, colour and place are measured from a reference in its own language and build, never carried over from another client's or guessed. A value with no reference ships only as a best estimate, marked provisional where it stands with what it was estimated from. A wiki crop of one dialog or button row with no whole frame behind it gives its colours and glyphs but no scale: a compare shoots at the reference's own size, so its unit is the crop's and not the game's, and the screen's size is a best estimate held provisional, with a whole frame on the References sought list and a queue item until one is found. A public video that letterboxes the game is sampled outside the repository into a labelled screenshot cropped to the game's screen there, and scored over a `region` clear of watermarks; its edges are the video's softness, so a clean score there is an outline of about a percent.

- **A reference judges the state its map entry records.** A region reference scores only the region it names, and a reference shot in other props, or of another variant, judges that state and not the base image. `approve` then prints `not the whole screen`, writes the image of the state it was asked for, and reports no score. A variant's image is written with `--variant` and named `Index-<variant>.png` (`FIXTURE_VARIANT_SEPARATOR`, a dash, since the repository's `ID_SEPARATOR` is a character Windows rejects in a file name). Its score is reported only when the entry records that variant as its `variant`.

- **An agent's verdict on a reference is a lead until it is checked.** A claim that a reference shows the wrong frame, the wrong recording or a defect is checked against the entry's `region`, `plate`, `props` and the comment above it, and by looking at the frame, before the reference or the entry changes. Only a mechanical finding, such as a missing file or a wrong dimension, is acted on at once.
- **`fetch` does not re-cut a reference.** It reports a missing file and never checks one already on disk, so a frame can outlive the `source` its entry was repointed from. Before a verdict rests on a reference, run `genshin:parity verify` on the machine that holds the recordings.

- **`approve` writes one screen's image through the suite.** It runs the suite's `-u` for that screen's test alone, never the whole suite, so no other screen's image moves, with the exact compare that `openspec/specs/genshin/parity/visual-suite/design.md` owns. A reference whose committed file is missing is an error that names its id and the path to add, so `approve` never writes an image against a reference it cannot read; a plate missing from the references folder is named the same way. The compare's row is written to the committed report before the image whenever the compare produced a score, whether or not the score clears the bar; a status with no score (`no reference`, `compare failed`, `not the whole screen`) writes no row.

- **A run writes only what is missing.** A whole-suite run never replaces an existing image without the update option, so a mismatch is listed after the cases and its image stays as it was. A screen with no image is written beside its component by the run where the update mode writes new images, which is the default outside CI; under CI the shot goes to the suite's diffs folder instead, and the case is counted with the screens that have no image. A moving screen is held still for the suite by its fixture's `stillProps`, which the parity page and the references never read, so the page and the references keep drawing it as it moves.

- **`genshin-interface`'s components have fixtures and images too**, shot to their own box at 1080 high, and its suite fails for a component without a fixture. Those components have no reference in the map and are not screens on the parity page, so `approve` does not write their images; their suite's run writes a missing one, and a run with `-u` takes each render as its new image.

- No person writes images by hand. `approve` writes them from the render and prints the status before it does, and a run writes only what is missing.

- **A bar moves only once its gap is the floor.** A screen over its bar reports the score and names the gap; while that gap is still fixable, the bar stays where it is. A looser bar is proposed only after nothing more can be cut without losing quality.

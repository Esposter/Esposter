# Build Conventions (tsdown)

The mechanism — what runs, in what order, and why — is `apps/web/content/docs/architecture/build-pipeline.md`. This skill is the conventions you apply when editing it.

## Settled — do not re-propose

Every line here is a direction a reader reaches for on meeting the rules below. Each was tried or considered; the argument is where the line points.

- **Finishing the source split** — giving the app's Vite and Nitro builds, or its Vitest project, the `source` condition. The package whose stores rely on its own build's auto-import injection breaks outright; reach for `watch:packages` (`references/source-exports.md`).
- **`devExports: true`** in place of the condition name. It points every condition at source, and Node's own loader reads no TypeScript (`references/source-exports.md`).
- **A repo-namespaced condition** (`esposter-source`), to stop a stranger's resolver matching the arm. Nothing published carries a source arm at all (`references/source-exports.md`).
- **A hand-maintained `onlyBundle` allowlist**, to answer tsdown's standing hint. `inlinedDependencies` already records every vendored package, and a new package's first build could never pass the check (`references/opt-outs.md`).
- **A guard that skips barrel generation on a hash of the file list.** A colliding rename changes ctix's output while moving no path, and the `package-builds` cache already gives what a sound key would (`references/barrels.md`).
- **Making barrel generation cheaper, or building the packages more concurrently.** ctix's cost is the dependency type surface and the wall time is one topological chain, so neither lever moves; the `build:prepare` hook, the `package-builds` cache and `watch:packages` already answer it (`references/barrels.md`).
- **Vendoring CJS dependencies as a policy.** It is a named exception per dependency; generalised it vendors the same library into half the dists here (`references/opt-outs.md`).
- **Bundling a dependency to spare the consumer an install.** It saves nothing and splits the dependency's types into two that fail `instanceof` (`references/dependency-placement.md`).
- **Dropping `composite` from `tsconfig.library.json`**, on the reading that nothing consumes it. It is the precondition for `isolatedDeclarations`; without it every package fails `TS5069` (`references/tsconfig-presets.md`).
- **A `compilerOptions` block in `tsconfig.build.base.json`, or a `paths` block in `tsconfig.base.json`.** The first emits declarations against the wrong lib set; the second shadowed real package names (`references/tsconfig-presets.md`).
- **Hashing `.github/` into either build cache key.** Every command those workflows run is already hashed through a manifest, so the key would move on every comment edit and pay the app build for a change no build can observe (`apps/web/content/docs/architecture/monorepo-tooling.md`, "CI job shape").
- **Filling a published package's metadata fields** — `engines`, `repository.directory`, a `LICENSE` beside the `license` the manifest names. None is derived by the build or checked by a gate, and a licence cannot be shared by symlink (`apps/web/content/docs/architecture/rejected/published-package-metadata.md`).

## Shared configs

A package's `tsdown.config.ts` is one factory call plus what is genuinely its own, composed with `mergeConfig` — a spread of a `getTsdownConfiguration*()` is a `no-restricted-syntax` error, since it drops every nested option the factory set; barrels are generated by the build (`references/shared-configs.md`, `references/barrels.md`).

## Externalized is the default — bundling is the exception

The manifest decides, not the config: `dependencies` and `peerDependencies` are externalized, `devDependencies` the source imports are bundled, a peer is listed once and only for a singleton, and a manifest names only what its own code imports (`pnpm lint:unused`). Never bundle to spare a consumer an install. Every `deps` entry goes through `getPackagePatterns` so a subpath import matches (`references/dependency-placement.md`).

## Every bundle's externals are gated — `references/gates.md`

`deps.onlyImport` applies to **every** package: a bundle may leave external only what its own manifest names, which turns a published package importing a private sibling, and a specifier that resolved to nothing, into a build error here rather than a runtime one in a consumer. Absence of `private` switches on `publint` and `attw` besides, and neither is ever disabled to get a build through. **What each gate catches and the fix when one fires** is that page.

## Self-alias and source exports — `references/source-exports.md`

A package refers to its own source through Node subpath imports (`"imports": { "#src/*": "./src/*.ts" }`), never `@/` — `apps/web` is the one tree that keeps `@/`, because Nuxt generates those aliases and nothing bundles the app from source. That is what lets `getTsdownConfiguration` give every package a second `source` export arm pointing at its TypeScript. **Writing a specifier that has to survive a sibling bundling this package, or deciding what the `source` condition reaches**, is that page — its two rejected variants are in `Settled` above.

## Dist size is the correctness signal

Every package snapshots its `dist` size in `src/index.test.ts`; a jump is something newly bundled, never a `-u` to take, and an export added to a bundled package moves `apps/functions`' and `apps/infra`'s snapshots too (`references/dist-size.md`).

## tsconfig presets and the bootstrap package — `references/tsconfig-presets.md`

Presets live in `@esposter/configuration` and are extended by path; the base carries no framework assumption. **Editing a preset, or changing `@esposter/configuration` itself** — which is built by the factories it exports, and is exempt from rules that would make its build a cycle — is that page.

## Dependency installs & workspace graph

Covered by root `CLAUDE.md` (`pnpm i`, `pnpm graph:gen`) and `apps/web/content/docs/architecture/monorepo-tooling.md` (install safety rules). One addition: if `pnpm i` needs network access, request approval for plain `pnpm i` rather than changing pnpm store settings.

## Reference pages

- `references/barrels.md` — when a generated `src/index.ts`, `exportsGeneration`, or the `entry` the build hook needs is in question.
- `references/opt-outs.md` — when a package minifies a deploy artifact, vendors what the default externalizes, or declares an entry field a host loads by convention.
- `references/side-effects.md` — when setting `sideEffects`, or a bundle loads and never runs a trigger (`scripts/src/workspace/sideEffects.test.ts` enforces that every package answers).
- `references/declarations.md` — when a package holds an ambient `.d.ts` no entry imports, or wraps a library a plugin augments.
- `references/dependency-placement.md` — when adding, moving or removing a dependency, or deciding whether one is bundled.
- `references/shared-configs.md` — when writing a package's `tsdown.config.ts` or a configuration factory.
- `references/dist-size.md` — when a size snapshot moves after a manifest, `deps`, factory or export change.

# Build Conventions (tsdown)

The mechanism — what runs, in what order, and why — is `openspec/specs/architecture/build-pipeline/design.md`. This skill is the conventions you apply when editing it.

## Settled — do not re-propose

Every line here is a direction a reader reaches for on meeting the rules below. Each was tried or considered; the argument is where the line points.

- **Finishing the source split** — giving the app's Vite and Nitro builds, or its Vitest project, the `source` condition. The package whose stores rely on its own build's auto-import injection breaks outright; reach for a rebuild of the package (`references/source-exports.md`).
- **`devExports: true`** in place of the condition name. It points every condition at source, and Node's own loader reads no TypeScript (`references/source-exports.md`).
- **A repo-namespaced condition** (`esposter-source`), to stop a stranger's resolver matching the arm. Nothing published carries a source arm at all (`references/source-exports.md`).
- **A hand-maintained `onlyBundle` allowlist**, to answer tsdown's standing hint. `inlinedDependencies` already records every vendored package, and a new package's first build could never pass the check (`references/opt-outs.md`).
- **A guard that skips barrel generation on a hash of the file list.** Generation costs milliseconds, and CI's traced task cache already gives what a sound key would (`references/barrels.md`).
- **ctix, or any barrel generator that loads a TypeScript program.** ctix dropped a name exported twice from the barrel with exit 0 and every check green, and its program was most of a package's build; `export *` lines from rolldown's oxc parse make the same collision `TS2308` (`references/barrels.md`).
- **Per-file `exports` for the barrel packages, the Nuxt module's shape.** Its glob entries exist because Nuxt loads each runtime file by path; everywhere else the flat `.` export is what every sibling imports and the one size snapshot, and tsdown's default single entry is the shape (`references/barrels.md`).
- **Building the packages more concurrently.** The wall time is one topological chain through the siblings' generated barrels (`references/barrels.md`).
- **A `tsconfig.build.json` in every package.** tsdown's transform reads `compilerOptions`, which the build preset has none of, and a declaration program seeded from the entries never reads an exclude — every other package's `dist` is byte-identical against `tsconfig.json`. Only the Vue build's `eager` program is loaded from the file list, so it alone keeps one (`references/tsconfig-presets.md`).
- **Vendoring CJS dependencies as a policy.** It is a named exception per dependency; generalised it vendors the same library into half the dists here (`references/opt-outs.md`).
- **Bundling a dependency to spare the consumer an install.** It saves nothing and splits the dependency's types into two that fail `instanceof` (`references/dependency-placement.md`).
- **Dropping `composite` from `tsconfig.library.json`**, on the reading that nothing consumes it. It is the precondition for `isolatedDeclarations`; without it every package fails `TS5069` (`references/tsconfig-presets.md`).
- **A `compilerOptions` block in `tsconfig.build.base.json`, or a `paths` block in `tsconfig.base.json`.** The first emits declarations against the wrong lib set; the second shadows real package names (`references/tsconfig-presets.md`).
- **Hashing `.github/` into a package build's or the app build's task cache input.** Every command those workflows run is already hashed through a manifest, so the key would move on every comment edit and pay the app build for a change no build can observe (`openspec/specs/architecture/monorepo-tooling/design.md`, "CI job shape").
- **Filling a published package's metadata fields** — `engines`, `repository.directory`, a `LICENSE` beside the `license` the manifest names. None is derived by the build or checked by a gate, and a licence cannot be shared by symlink (`openspec/rejected/architecture/published-package-metadata/design.md`).

## Rules

- **A package's `tsdown.config.ts` is one factory call plus what is genuinely its own, composed with `mergeConfig`** — a spread of a `getTsdownConfiguration*()` drops every nested option the factory set (`no-restricted-syntax`); barrels are generated by the build (`references/shared-configs.md`, `references/barrels.md`).
- **The manifest decides what is bundled, not the config**: `dependencies` and `peerDependencies` are externalized, the `devDependencies` the source imports are bundled, a peer is listed once and only for a singleton, and a manifest names only what its own code imports (`vp run lint:unused`) — never bundle to spare a consumer an install (`references/dependency-placement.md`).
- **A manifest's `files` is the tarball: `dist` and what a runtime reads beside it for a built package, its directories less `!**/*.test.ts` and `!.claude-plugin/types` for a plugin shipping its source** — only a release reads the list, so `scripts/src/workspace/publishedFiles.test.ts` packs every published package (`openspec/specs/architecture/monorepo-tooling/design.md`, "Lerna Lite").
- **Every `deps` entry goes through `getPackagePatterns`**, so a subpath import matches (`references/dependency-placement.md`).
- **`deps.onlyImport` gates every bundle's externals, and a published package adds `publint` and `attw`** — none is ever widened or disabled to get a build through (`references/gates.md`).
- **A package reaches its own source through `#src/*` subpath imports, never `@/`**, which is what gives every package its `source` export arm; `apps/web` keeps `@/` because Nuxt generates it (`references/source-exports.md`).
- **A moved `dist` size snapshot is something newly bundled, never a `-u` to take** — and an export added to a bundled package moves `apps/functions`' and `apps/infra`'s snapshots too (`references/dist-size.md`).
- **A package that is a Nuxt module builds its runtime unbundled beside a `src/module.ts` entry, and the app registers it by the path to that source**, never its package name, which `nuxt prepare` cannot load before the packages build (`references/nuxt-module-packages.md`).
- **Presets live in `@esposter/configuration`, extended by path, and the base carries no framework assumption** (`references/tsconfig-presets.md`).
- **A data set a browser reads is published, never imported**, so no build bundles it and no declaration program reads it: `genshin-world` imports only its lock and one save bound, and the build tsconfig maps no generated path (the `genshin-data` skill, `openspec/specs/architecture/build-pipeline/design.md`).
- **A package is built through its vp task: `vp run build:<directory>`, or `vp run build:packages` for every package.** The root `vite.config.ts` generates one task per package from its manifest's `build` script. It runs in the package's directory, after the tasks of the workspace packages it depends on, and vp's task cache replays its `dist` when its inputs are unchanged. The task keeps its own rewritten files (the barrels, `dist`, the `_tmp_*` manifest write) out of its inputs, which is what lets it cache at all. The cache lives in `node_modules/.vite/task-cache` of each checkout, so a fresh worktree builds cold once.
- **Installs and the workspace graph are `AGENTS.md` and `openspec/specs/architecture/monorepo-tooling/design.md`** — where `pnpm i` needs the network, ask for plain `pnpm i` rather than changing pnpm store settings.

## Reference pages

- `references/gates.md` — when `deps.onlyImport`, `publint` or `attw` fails a build, or a consumer reports a module the package never referenced.
- `references/source-exports.md` — when a package imports its own source, a specifier has to survive a sibling bundling it, or the `source` condition's reach is in question.
- `references/tsconfig-presets.md` — when editing a `tsconfig*.json` preset, or `@esposter/configuration` itself.
- `references/barrels.md` — when a generated `src/index.ts`, `exportsGeneration`, or the `entry` the build hook needs is in question.
- `references/opt-outs.md` — when a package minifies a deploy artifact, vendors what the default externalizes, or declares an entry field a host loads by convention.
- `references/side-effects.md` — when setting `sideEffects`, or a bundle loads and never runs a trigger (`scripts/src/workspace/sideEffects.test.ts` enforces that every package answers).
- `references/declarations.md` — when a package holds an ambient `.d.ts` no entry imports, or wraps a library a plugin augments.
- `references/dependency-placement.md` — when adding, moving or removing a dependency, or deciding whether one is bundled.
- `references/shared-configs.md` — when writing a package's `tsdown.config.ts` or a configuration factory.
- `references/dist-size.md` — when a size snapshot moves after a manifest, `deps`, factory or export change.
- `references/nuxt-module-packages.md` — when a workspace package is a Nuxt module, or the app registers one.

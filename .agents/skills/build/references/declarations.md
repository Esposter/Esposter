# Declarations that a bundle cannot carry

Read when a package holds an ambient `.d.ts` no entrypoint imports, or wraps a library whose types a plugin augments.

## Ambient declarations are in the declaration program

A Vue package's `.vue` declarations are generated by `tsrs` over its `tsconfig.build.json`, so the declaration program is that tsconfig's file list, not the entrypoints. `getTsdownConfigurationVue` names the tsconfig for that reason. An ambient `.d.ts` that nothing imports — `auto-imports.d.ts`, generated by `unplugin-auto-import` — is in the program through the tsconfig's `include`, so every symbol it declares is typed in the shipped types. A declaration build that seeds its program from the entrypoints leaves such a file out, and every symbol it declares resolves to `any` in the shipped types. That fails silently: the type check and the build pass, and the consumer gets `declare const useSomeStore: any`.

A new ambient file has to sit where the package's tsconfig `include` reaches it. No size test catches a collapse, since it makes `index.d.ts` smaller and a ceiling fails only growth (`references/dist-size.md`). The check is the shipped file: the exported types the ambient file declares must read as typed in `index.d.ts`, with none of them `any`.

## Module augmentations do not cross a package boundary

A `declare module "x"` augmentation — a library plugin, a Zod extension, a module's own type map — is resolved **per TypeScript program** against that module's identity. It is not a value, so it cannot be re-exported, and it does not travel inside a bundled `.d.ts`. Neither an `import type {} from "the-plugin"` nor a `/// <reference types="…" />` in the source survives the bundle, and externalizing the dependency changes nothing: the consumer's own program still has to contain the plugin's declarations before the augmented member resolves.

So a package that wraps an augmented library exports the **value** and registers the augmentation at module scope so the runtime works everywhere, while every package that _types_ an augmented member still imports the plugin in its own graph. Don't chase this with a barrel re-export or a reference directive; both look like they work until a downstream `vp run typecheck` reports the member missing.

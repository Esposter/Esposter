# Re-cut

A window the bot will not review is handed back to the opener, cut smaller, rather than left to hold the stack.

## The skipped review and the ask

- **A skipped review is asked for, a wait apart, and then cut again.** The window next to merge is asked — a window above it waits its turn, asked for nothing ([gate and merge](/docs/infra/review-collector/collection-cycle/gate-and-merge)) — with `@coderabbitai review` carrying a hidden marker, and only the collector's own marked asks count — a person's ask spends none of them. Each ask is followed by a wait (`REVIEW_ASK_WAITS_MS`, whose length is the ask cap); the bot's answer fires the cycle sooner, and otherwise the retrigger wakes the walk when the wait ends. Once the wait after the last ask has passed with the bot still skipping, the window is too big for one review, and it is re-cut: `develop` moves back below it under a lease — to the window below, or to where a bottom window last met `main` — and the window and every window stacked above it are closed with their branches deleted, top first, each with a marker comment naming the cap its replacement is cut to, half the cap it was cut under. Their commits are still on `ai/queue`, so the queue owes them again and the opener cuts them anew in the same run: the first replacement under that cap, read off the newest window's marker, and the windows after it under the plan's cap again. A replacement skipped in turn is re-cut at half of its own cap, so the cap keeps halving until a review runs. **A re-cut's cap is held where the re-cut window stood** (`getWindowFileCap`). The next window is cut to the plan's cap when no window pull request exists at all, and when no window is open and the newest window's base is a window branch, since its count then reads against `main` with nothing stacked under it (the port, below). In every other case it is cut to the newest window's re-cut cap, or to the plan's when that window carries none (one never re-cut): a replacement waiting out a stack below keeps the cap it was given, since its count reads against the window below, and a window re-cut from `main` keeps its cap with nothing open, since that is where its replacement stands too. Dropping the cap in either place would cut the size the bot has already skipped, time after time. A bottom window with no CodeRabbit check at all is asked the same way once it has waited `MISSING_CHECK_WAIT_MS` since it opened, and the retrigger wakes the walk at the end of that wait; a window above it with no check simply waits its turn. **A review pending past `PENDING_CHECK_WAIT_MS` is one the bot dropped**, and is asked the same way: a window's review takes a fraction of that wait, and a dropped one sends no status event to say so, so the wait counts from the status that set the check pending, read off the pull request's status rollup since `gh pr checks` gives a commit status no start. Every run that finds the bottom window pending sets the retrigger for the end of that wait, so a status event that never comes strands nothing, and a start it cannot read counts from that run, since an ask over a running review cancels it. The ask is owed only while the re-read still shows the check pending — a review that finished meanwhile is the next run's verdict — and an ask that restarts the review starts the wait again from the new status. An ask the re-read withholds — the check moved under the run, or could not be read — is read again `CHECK_REREAD_DELAY_SECONDS` later: the event a moved check sent may have landed on the run that was ending, and an unreadable one sends none. Nothing in the walk fails the run, so one window's hold never leaves another's settlement unmade.

## The release before the stack

- **The release before the stack.** A pull request from `develop` to `main` that predates the stack is the stack's bottom while it is open: it is gated on its one review exactly as a window is, merged once that review completes, and its findings drained after the merge. It is never retargeted, and `develop` is never deleted. While it is open no window opens, since a cut over `develop` would move its head under its own review; once merged, `main` has moved past `develop`, the stroke follows it, and the windows open. Closed without merging by a person, it pauses the collector as a closed window does. Skipped, or refused by a limit that leaves every ask unanswered, it goes through the same asks and waits, and past the last one it is re-cut as a bottom window is, with what `develop` being its head changes: it is closed first, with the re-cut marker and its branch kept, since moving a pull request's head back onto its base under it leaves GitHub to close or merge it by its own reading; then `develop` moves back under a lease to where it last met `main`, and the opener cuts its commits into windows in the same run — the release read again after the walk, since nothing fires a run when it closes — under the plan's cap rather than half of it, since no cap ever measured a release a person opened. A release a re-cut closed is no pause. A release the bot keeps skipping past its last ask is re-cut as a bottom window is, so no window waits behind a pull request no review will ever read. The collector finishes on its own: only billing, the token and a window a person closes are left to a person, and a commit past its caps to a session, from its issue.

## A window off the chain

- **A window off the chain is cut again.** The walk merges and retargets only along the chain from `main`, each window on the head of the one below, and a window off it — above a fork, or on a base no open window carries — has no base a merge or a retarget could trust. So before the walk every window off the chain is given back to the opener the way a re-cut gives one back (`settleWindowChain`): `develop` moves back under a lease to the top of the chain, or to where it last met `main` when none is left, and each is closed with its branch deleted and the marker naming the cap it was cut under. A lease refused because `develop` moved under the run closes nothing, and the run wakes a minute later (`MOVED_BRANCH_RETRY_DELAY_SECONDS`), since a push to `develop` fires none. The opener cuts its commits again, and the replacement's opening asks for its review afresh. The release from `develop` is never closed, its head being `develop`, nor is `develop` moved while it is open. A fork or a gap in the chain is re-cut, never a failed run: the collector finishes its own work unattended, and nothing but billing and the token may wait for someone. A re-cut spends one review where a red run would spend every review until someone looks.

## A re-cut window's findings

**A re-cut window's findings are carried to the window that replaces it.** A re-cut can close a window whose review already completed — a fold past its attempts, a window off the chain — and its commits come back in the window above it, or the first of several. That window's drain answers the closed windows directly below it as well, one session each, newest first, up to the first that is not a re-cut one (`readCarriedPullRequests`), and the cut that carries the fixes replies on them as on the window itself. The replacement's drain runs against a `develop` that carries the same code again. Draining the closed window before its re-cut is the alternative, and the code does not allow it: the fixes lead the next window from `ai/review-fixes`, which sits on `develop`, and the re-cut moves `develop` back below the very code they touch, so each would meet the sync as a conflict with nothing to apply to.

## Notes

- **A re-cut reads the cap a window was cut under off the windows below it as they stand now.** A replacement opened over the stack and retargeted to `main` once the window below merged reads as one cut from `main`, so a re-cut of it halves the plan's cap rather than the smaller one it had: one more skipped window in that chain, the price of reading no record of the stack each window opened over.
